## 2. 一句话概括

员工对用户提交的“存入积分申请”执行审核：

- 拒绝时只更新申请状态；
- 通过时，根据审核发生时间、当前营业时段、用户上一次审核通过的存分时间以及此后已批准的取分记录，计算实际到账积分；
- 增加用户积分；
- 写入积分明细和综合交易流水；
- 按条件增加用户金币余额并写入余额交易流水。

---

## 3. 业务背景与核心概念

### 3.1 存入积分申请

用户先提交一个存入积分申请，申请保存在 `save_points` 表中。

申请中最重要的两个积分字段是：

| 字段 | 含义 |
| --- | --- |
| `save_points` | 用户原始申请存入的积分数量 |
| `points` | 提交申请时预先计算的积分数量，当前创建逻辑固定为 `save_points ÷ 5` |

审核方法真正给用户增加的积分，并不直接使用申请表中的 `points` 字段，而是重新计算。

### 3.2 用户当前积分

审核通过后，实际积分增加到 `users.points`。

该字段是当前业务中的可见积分余额。

系统中同时还存在：

- `users.total_points`
- `users.used_points`

本审核方法不会更新这两个字段。

### 3.3 取分记录

用户从账户提取积分时，会创建 `points_withdrawal` 记录。

审核存分时，只统计：

- 当前用户的记录；
- `audit_status = approved` 的记录；
- 处于本次基数统计时间区间内的记录。

取分记录中的 `points` 总和被称为“基数积分”。

### 3.4 基数积分

基数积分不是用户当前余额，也不是用户历史累计积分。

它表示：

```text
从本营业时段开始，或从本营业时段内上一次存分审核通过时间开始，
到本次审核发生之前，
用户所有已批准取分记录的积分总和。
```

### 3.5 实际到账积分

实际到账积分是本次审核通过后真正增加到 `users.points` 的数量。

它可能与以下字段不同：

- 用户申请的 `save_points`；
- 申请创建时写入的 `save_points.points`。

### 3.6 金币

本功能中的“金币”实际增加到用户的 `users.balance`。

`users.balance` 是两位小数余额字段。

## 4. 上游：用户如何创建存分申请

审核方法处理的申请由小程序接口创建：

- 请求方式：`POST`
- 请求地址：`/api/mini/user/points/save`
- 认证方式：小程序 JWT

用户提交：

- `points`：原始存入积分；
- `store_id`：提交到的门店。

当前提交规则：

1. `points` 必须能够转换为大于或等于 1 的整数；
2. `store_id` 必须有值；
3. 系统创建一条 `save_points`；
4. `save_points.save_points` 保存原始积分；
5. `save_points.points` 保存原始积分除以 5 的结果；
6. 状态使用数据库默认值 `1`，表示待审核。

申请创建时没有严格验证：

- 门店是否存在；
- 用户是否允许向该门店提交；
- 是否有重复申请；
- 积分来源是否合法；
- 申请数量是否超过业务上限。

## 5. 审核接口入口

### 5.1 请求信息

- 请求方式：`POST`
- 请求地址：`/api/mini/management/audit/points`
- 路由分组：`mini/management`
- 认证中间件：`miniprogram.jwt`
- 认证 Guard：`api`

### 5.2 当前认证范围

路由要求请求者必须是一个有效的小程序登录用户。

JWT 中间件会：

1. 解析 Token；
2. 验证 Token；
3. 取得用户；
4. 确认用户状态允许登录；
5. 将默认 Guard 切换到 `api`。

### 5.3 业务上应具备的身份要求

从业务命名和审核列表方法可以推断，执行审核的人应当满足：

1. 用户类型为 `staff`；
2. 员工绑定了门店；
3. 员工只能审核所属门店的存分申请。

但是，当前 `audit` 方法本身没有执行这些检查。

审核列表 `orderList` 会检查：

- 当前用户存在；
- `user_type = staff`；
- 当前员工有 `store_id`；
- 只查询员工所属门店的待审核申请。

审核写接口没有重复使用这些条件。

因此当前真实行为是：

- 任何通过小程序 JWT 认证的用户都可能调用审核接口；
- 普通顾客也可能提交审核请求；
- 审核人可以传入任意申请 ID；
- 没有确认申请是否属于审核人的门店。

## 6. 请求参数

| 参数 | 业务上必填 | 当前代码类型预期 | 说明 |
| --- | --- | --- | --- |
| `id` | 是 | 整数 | `save_points` 申请 ID |
| `type` | 是 | 整数 | 审核结果状态 |

### 6.1 状态值

`save_points.status` 的数据库定义为：

| 值 | 含义 |
| ---: | --- |
| `1` | 待审核 |
| `2` | 审核确认/审核通过 |
| `3` | 审核拒绝 |

当前方法只有在：

```text
intval(type) === 2
```

时才发放积分和金币。

其他值只更新申请状态，不发放任何资产。

### 6.2 当前缺少的参数验证

当前方法没有使用统一验证器，也没有显式验证：

- `id` 是否存在；
- `id` 是否为正整数；
- `type` 是否存在；
- `type` 是否为整数；
- `type` 是否只能为 2 或 3；
- 申请是否仍为待审核；
- 申请是否属于当前员工门店；
- 当前用户是否为员工；
- 拒绝时是否填写原因。

### 6.3 缺失参数的实际风险

模型方法声明要求整数参数。

如果 `id` 或 `type` 缺失、为空或无法转换为整数，可能触发 PHP 类型错误。

当前外层只捕获 `Exception`，而部分类型错误属于 `Error`/`TypeError`，不一定被当前异常捕获逻辑处理，可能直接表现为服务器错误。

## 7. 审核事务总流程

审核方法一开始就开启数据库事务。

完整顺序为：

```text
开始事务
-> 读取 id 和 type
-> 查询存分申请
-> 更新申请状态、审核人和审核时间
-> 如果 type=2，计算实际积分
-> 增加用户积分
-> 写 user_points
-> 写积分 transaction_records
-> 计算金币
-> 如果金币大于0，增加用户余额
-> 写余额 transaction_records
-> 提交事务
-> 返回审核成功
```

如果 `type` 不是 2：

```text
开始事务
-> 查询存分申请
-> 更新申请状态、审核人和审核时间
-> 不计算积分
-> 不增加积分
-> 不增加金币
-> 提交事务
-> 返回审核成功
```

---

## 8. 查询存分申请

系统根据请求中的 `id` 查询 `save_points`：

```text
where id = 请求 id
```

查询没有附加：

- `status = 1`；
- `store_id = 当前员工门店`；
- 用户范围；
- 行锁。

如果没有找到申请，当前方法返回：

```text
订单异常
```

这里把存分申请称为“订单”。

### 8.1 事务处理问题

查询不到申请时，方法直接返回错误，没有显式执行：

- `DB::rollBack()`；
- `DB::commit()`。

因此该请求在返回时可能仍留有未显式结束的数据库事务，最终行为依赖框架和连接生命周期。

---

## 9. 更新审核状态

找到申请后，系统立即更新：

| 字段 | 写入内容 |
| --- | --- |
| `status` | 请求中的 `type` |
| `verify_staff` | 当前 `api` Guard 用户 ID |
| `verify_time` | 当前服务器时间 |
| `updated_at` | ORM 自动更新为当前时间 |

### 9.1 当前更新条件

实际更新条件只有：

```text
id = 申请 ID
```

没有要求：

- 原状态必须为待审核；
- 当前记录未被其他员工处理；
- 当前记录属于当前员工门店；
- `type` 必须为通过或拒绝。

### 9.2 更新失败

如果更新结果为假，返回：

```text
审核失败
```

这里同样没有在返回前显式回滚事务。

---

## 10. 审核拒绝行为

当 `type = 3` 时，当前方法只执行：

1. 将申请状态改成 3；
2. 保存审核员工 ID；
3. 保存审核时间；
4. 提交事务；
5. 返回“审核成功”。

不会执行：

- 增加用户积分；
- 创建 `user_points`；
- 创建积分交易流水；
- 计算金币；
- 增加用户余额；
- 创建余额交易流水。

当前接口不接受审核备注或拒绝原因。

---

## 11. 审核通过行为

当 `type = 2` 时，系统执行以下资产处理：

1. 计算本次实际到账积分；
2. 读取用户变更前积分；
3. 增加用户积分；
4. 读取用户变更后积分；
5. 生成积分记录描述；
6. 创建 `user_points` 积分明细；
7. 创建积分类型的综合交易流水；
8. 根据规则计算金币；
9. 金币大于零时读取变更前余额；
10. 增加用户余额；
11. 读取变更后余额；
12. 创建余额类型的综合交易流水；
13. 提交事务。

---

## 12. 审核计算采用的时间

计算规则使用的是：

```text
审核执行时的服务器当前时间
```

不是：

- 用户提交申请的时间；
- 申请 `created_at`；
- 请求客户端时间；
- 业务人员选择的时间；
- `verify_time` 字段读取值。

因此同一笔申请在不同时间审核，可能得到不同的实际积分和金币。

## 13. 营业时段划分

业务营业时段定义为：

```text
当天 17:00:00 至次日 10:00:00
```

一个营业时段跨越两个自然日。

### 13.1 00:00 至 09:59:59

如果审核时间的小时小于 10：

- 该时间属于前一天开始的营业时段；
- 营业日期取前一天；
- 营业开始时间为前一天 17:00；
- 营业结束时间为当天 10:00。

示例：

```text
审核时间：2026-07-26 03:20
营业日期：2026-07-25
营业开始：2026-07-25 17:00
营业结束：2026-07-26 10:00
```

### 13.2 10:00 至 16:59:59

如果审核时间位于 10:00 至 17:00 之前：

- 视为非营业时间；
- 不计算取分基数；
- 直接按标准五分之一规则计算积分；
- 金币按原始存入积分计算。

示例：

```text
审核时间：2026-07-26 12:00
结果：非营业时间，使用标准规则
```

### 13.3 17:00 至 23:59:59

如果审核时间的小时大于或等于 17：

- 该时间属于当天开始的营业时段；
- 营业日期为当天；
- 营业开始时间为当天 17:00；
- 营业结束时间为次日 10:00。

示例：

```text
审核时间：2026-07-26 20:30
营业日期：2026-07-26
营业开始：2026-07-26 17:00
营业结束：2026-07-27 10:00
```

### 13.4 精确边界

按当前小时判断：

| 时间 | 归类 |
| --- | --- |
| `09:59:59` | 营业时段 |
| `10:00:00` | 非营业时段 |
| `16:59:59` | 非营业时段 |
| `17:00:00` | 营业时段 |

## 14. 查找本营业时段内的上一次存分

只有审核发生在营业时段内时，系统才查找上一次存分。

查询条件：

1. `user_id` 等于当前申请用户；
2. 排除当前申请 ID；
3. `status = 2`，即已审核通过；
4. `updated_at >= 营业开始时间`；
5. `updated_at < 本次计算时间`；
6. 按 `updated_at` 倒序；
7. 取第一条。

### 14.1 使用 `updated_at` 的原因

代码将 `updated_at` 视为申请实际审核通过时间。

当申请状态被更新时，ORM 会同步修改 `updated_at`。

### 14.2 基数统计起点

如果找到上一次审核通过的存分申请：

```text
基数统计起点 = 上一次申请的 updated_at
```

如果没有找到：

```text
基数统计起点 = 本营业时段开始时间
```

### 14.3 查询范围限制

上一次存分查询只按用户查询，没有按门店查询。

因此用户在其他门店的审核通过记录，也会重置本门店的基数统计起点。

---

## 15. 计算基数积分

确定起点后，系统查询 `points_withdrawal`。

统计条件：

1. `user_id` 等于申请用户；
2. `audit_status = approved`；
3. `created_at >= 基数统计起点`；
4. `created_at < 当前计算时间`。

统计结果：

```text
基数积分 = 符合条件的取分记录 points 总和
```

### 15.1 时间字段

基数统计使用取分记录的 `created_at`。

不会使用：

- `withdrawal_date`；
- `withdrawal_time`；
- `audited_at`。

### 15.2 审核状态

只统计 `approved`。

当前取分创建方法虽然注释写“默认待审核”，实际创建时直接写入：

```text
audit_status = approved
```

所以正常创建的取分记录会立即参与基数统计。

### 15.3 门店范围

基数积分只按用户统计，不限制 `store_id`。

因此用户在其他门店的取分记录也可能计入本次基数。

### 15.4 营业结束时间

代码虽然计算了 `businessEnd`，但它只用于日志。

查询中没有直接使用：

```text
created_at < businessEnd
```

由于当前时间本身处于本营业时段，通常不会跨出结束时间，但 `businessEnd` 并没有成为数据库查询约束。

## 16. 实际到账积分规则

定义：

```text
S = 用户原始申请存入积分，即 save_points.save_points
B = 本次计算出的基数积分
A = 实际增加到用户账户的积分
E = 超出基数的积分
```

### 16.1 非营业时间

审核时间在 10:00 至 16:59:59：

```text
A = 向下取整(S ÷ 5)
E = 0
hasDiscount = false
```

系统不会查询基数积分。

### 16.2 营业时间，但基数为零

审核发生在营业时段，但符合条件的取分合计小于或等于零：

```text
A = 向下取整(S ÷ 5)
E = 0
hasDiscount = false
```

### 16.3 营业时间，且 S 小于或等于 B

当原始存入积分不超过基数积分：

```text
A = 向下取整(S ÷ 5)
E = 0
hasDiscount = true
```

虽然变量名为 `hasDiscount = true`，实际到账仍然是五分之一。

基数中没有使用的剩余部分不会结转到下一次存分。

### 16.4 营业时间，且 S 大于 B

当原始存入积分超过基数积分：

```text
E = S - B
A = B + 向下取整(E ÷ 5)
hasDiscount = true
```

含义：

- 基数范围内的部分按 1:1 到账；
- 超过基数的部分按 1:5 到账。

### 16.5 决策表

| 审核环境 | 条件 | 实际积分 A | 超出部分 E | `hasDiscount` |
| --- | --- | ---: | ---: | --- |
| 非营业时间 | 任意 S | `floor(S/5)` | 0 | false |
| 营业时间 | `B <= 0` | `floor(S/5)` | 0 | false |
| 营业时间 | `0 < S <= B` | `floor(S/5)` | 0 | true |
| 营业时间 | `S > B > 0` | `B + floor((S-B)/5)` | `S-B` | true |

## 17. 实际积分计算示例

### 17.1 非营业时间

```text
审核时间：12:00
原始存入 S：5,000
实际积分 A：5,000 ÷ 5 = 1,000
超出部分 E：0
```

### 17.2 营业时间但没有取分基数

```text
审核时间：20:00
基数 B：0
原始存入 S：8,000
实际积分 A：8,000 ÷ 5 = 1,600
```

### 17.3 原始存入不超过基数

```text
审核时间：20:00
基数 B：3,000
原始存入 S：2,000
实际积分 A：2,000 ÷ 5 = 400
超出部分 E：0
```

当前规则不会因为基数为 3,000 就让这 2,000 按 1:1 到账。

### 17.4 原始存入超过基数

```text
审核时间：20:00
基数 B：3,000
原始存入 S：8,000
超出部分 E：8,000 - 3,000 = 5,000
实际积分 A：3,000 + 5,000 ÷ 5 = 4,000
```

### 17.5 多次存分后的基数窗口

假设营业开始时间为 17:00：

```text
17:30 用户取分 3,000
18:00 第一次存分审核通过
18:30 用户取分 1,000
19:00 第二次存分审核通过
```

第一次审核：

```text
基数统计区间：17:00 至 18:00
基数 B：3,000
```

第二次审核：

```text
基数统计区间：第一次审核通过时间至 19:00
基数 B：1,000
```

第一次审核前的 3,000 不会再次进入第二次计算。

---

## 18. 增加用户积分

计算出实际积分后，系统：

1. 查询用户，记录增加前 `users.points`；
2. 执行原子增量更新；
3. 增加数量为 `actualPoints`；
4. 再次查询用户，记录增加后 `users.points`。

变化公式：

```text
用户新积分 = 用户旧积分 + 实际到账积分
```

### 18.1 增加失败

积分增加失败时：

1. 回滚事务；
2. 返回“给用户存入积分失败”。

### 18.2 未更新的积分字段

该流程只增加：

```text
users.points
```

不会增加：

- `users.total_points`；
- `users.used_points`。

因此系统内不同积分字段可能继续产生差异。

---

## 19. 生成积分描述

积分增加后，系统重新根据当前时间和数据生成一段描述。

描述可能是以下形式。

### 19.1 非营业时间

```text
用户存入积分：S，实际存入积分：A（标准规则）
```

### 19.2 营业时间但无基数

```text
用户存入积分：S，实际存入积分：A（无基数积分）
```

### 19.3 S 小于或等于 B

```text
用户存入积分：S，基数积分：B，实际存入积分：A
（基数积分规则：存入≤基数）
```

### 19.4 S 大于 B

```text
用户存入积分：S，基数积分：B，超出部分：E，实际存入积分：A
（基数积分规则：存入>基数）
```

### 19.5 描述重新计算的风险

`calculateActualPoints` 和 `generatePointsDescription` 分别：

- 获取一次当前时间；
- 查询一次上次存分；
- 查询一次取分合计。

描述没有直接使用第一次计算时的基数结果。

如果两次调用之间：

- 新增了取分记录；
- 其他审核同时完成；
- 时间跨过 10:00 或 17:00；

则描述中的基数和实际用于发放积分的基数可能不一致。

---

## 20. 创建 `user_points` 积分明细

系统创建一条用户积分明细：

| 字段 | 内容 |
| --- | --- |
| `user_id` | 存分用户 ID |
| `points` | 实际到账积分 A |
| `type` | `earn` |
| `source` | `存入积分` |
| `description` | 根据营业时段和基数生成的详细说明 |

当前没有写入 `source_id`。

因此 `user_points` 不能仅通过结构化字段直接关联到对应的 `save_points` 申请，只能尝试通过用户、时间和描述判断。

### 20.1 创建失败

积分明细创建失败时：

1. 回滚事务；
2. 回滚申请状态；
3. 回滚用户积分增加；
4. 回滚事务内其他写入；
5. 返回“给用户创建积分记录失败”。

---

## 21. 创建积分综合交易流水

系统向 `transaction_records` 创建一条积分收入流水：

| 字段 | 内容 |
| --- | --- |
| `user_id` | 存分用户 |
| `amount_type` | `points` |
| `trans_type` | `1`，表示收入 |
| `amount` | 原始申请积分 S |
| `balance_before` | 增加前 `users.points` |
| `balance_after` | 增加后 `users.points` |
| `description` | 原始存入积分和实际获得积分 |
| `related_id` | `save_points` 申请 ID |

### 21.1 流水金额含义不一致

流水的 `amount` 保存的是：

```text
原始申请积分 S
```

但账户真实变化是：

```text
实际到账积分 A
```

因此可能出现：

```text
amount != balance_after - balance_before
```

示例：

```text
原始申请 S：8,000
实际到账 A：4,000
流水 amount：8,000
余额变化：4,000
```

### 21.2 流水保存结果

`TransactionRecords::userAddRecord` 返回保存结果，但当前调用没有检查返回值。

如果数据库层只是返回 false 而没有抛出异常，审核流程可能仍然提交，导致用户积分已增加但综合交易流水缺失。

## 22. 金币计算规则

积分处理完成后，系统计算金币。

定义：

```text
C = 计算得到的金币
S = 原始存入积分
E = 超出基数积分
```

### 22.1 `hasDiscount = true`

当营业时段内存在正数基数时，`hasDiscount` 为 true。

金币计算：

```text
C = E ÷ 2000
```

保留两位小数，使用 BCMath 截断而不是四舍五入。

如果 `S <= B`：

```text
E = 0
C = 0
```

### 22.2 `hasDiscount = false`

以下情况 `hasDiscount` 为 false：

- 非营业时间；
- 营业时间但基数小于或等于零。

金币计算：

```text
C = S ÷ 2000
```

同样保留两位小数并截断。

### 22.3 注释与实际公式冲突

代码注释写的是：

```text
积分 ÷ 1000
```

实际执行代码使用：

```text
积分 ÷ 2000
```

本文以实际执行的 `/2000` 为准。

### 22.4 金币决策表

| 场景 | 金币计算基数 | 实际公式 |
| --- | ---: | --- |
| 非营业时间 | 原始积分 S | `S/2000` |
| 营业时间、B<=0 | 原始积分 S | `S/2000` |
| 营业时间、0<S<=B | 0 | `0/2000 = 0` |
| 营业时间、S>B>0 | 超出部分 E | `E/2000` |

---

## 23. 金币计算示例

### 23.1 非营业时间

```text
S = 5,000
A = 1,000
C = 5,000 ÷ 2,000 = 2.50
```

金币使用原始积分 5,000，而不是实际积分 1,000。

### 23.2 营业时间，无基数

```text
S = 8,000
B = 0
A = 1,600
C = 8,000 ÷ 2,000 = 4.00
```

### 23.3 营业时间，S 小于或等于 B

```text
S = 2,000
B = 3,000
A = 400
E = 0
C = 0
```

### 23.4 营业时间，S 大于 B

```text
S = 8,000
B = 3,000
E = 5,000
A = 4,000
C = 5,000 ÷ 2,000 = 2.50
```

### 23.5 两位小数截断

```text
计算基数 = 1,999
1,999 ÷ 2,000 = 0.9995
BCMath 保留两位小数结果 = 0.99
```

不是四舍五入后的 `1.00`。

---

## 24. 判断是否发放金币

计算金币后，代码使用 `bccomp(coin, 0)` 判断金币是否大于零。

当前调用没有显式提供比较精度。

BCMath 在没有指定 scale 时使用全局 `bcscale`，如果系统没有另外配置，常见默认精度为 0。

这会产生重要影响：

- `0.50` 可能按 0 位精度与 0 比较，被视为不大于 0；
- 小于 1 的正数金币可能不进入发放流程；
- 具体结果依赖运行环境的全局 BCMath 精度配置。

因此当前行为并不完全由本方法自身决定。

---

## 25. 增加用户金币余额

当金币被判断为大于零时，系统：

1. 查询用户变更前 `balance`；
2. 调用 `User::incrementUserBalance`；
3. 查询用户变更后 `balance`；
4. 创建余额收入流水。

变化意图：

```text
用户新余额 = 用户旧余额 + 金币 C
```

### 25.1 参数类型造成的小数风险

`User::incrementUserBalance` 的余额参数声明为整数：

```text
int balance
```

但金币计算结果是两位小数字符串，例如：

```text
2.50
```

在非严格类型模式下，PHP 可能将其转换为整数：

```text
2.50 -> 2
```

这意味着当前实际入账可能丢失小数部分。

示例：

```text
计算金币：2.50
可能实际增加余额：2
```

同时，流水 `amount` 仍可能记录为 `2.50`，造成流水金额与余额真实变化不一致。

### 25.2 增加失败

余额增加失败时：

1. 记录“用户存入金币失败”日志；
2. 回滚事务；
3. 返回“存入余额失败”。

金币发放后，系统向 `transaction_records` 写入：

| 字段 | 内容 |
| --- | --- |
| `user_id` | 存分用户 |
| `amount_type` | `balance` |
| `trans_type` | `1`，表示收入 |
| `amount` | 计算得到的金币 C |
| `balance_before` | 发放前余额 |
| `balance_after` | 发放后余额 |
| `description` | 原始存入积分和获得金币 |

## 27. `save_points` 申请记录的最终数据

审核完成后，申请记录会保存：

| 字段 | 结果 |
| --- | --- |
| `status` | 请求中的审核类型 |
| `verify_staff` | 当前认证用户 ID |
| `verify_time` | 审核时间 |
| `updated_at` | 审核更新时间 |
| `save_points` | 保持用户原始申请积分，不变 |
| `points` | 保持申请创建时的 `save_points/5`，不变 |

### 27.1 `points` 字段不会回写实际结果

审核通过后，即使按基数规则实际到账积分高于五分之一，系统也不会把实际积分写回 `save_points.points`。

示例：

```text
原始申请 S：8,000
申请创建时 points：1,600
基数 B：3,000
审核实际到账 A：4,000
审核后 save_points.points：仍为1,600
```

因此：

```text
save_points.points 不一定等于用户实际获得积分
```

### 27.2 排行榜影响

当前排行榜统计的是审核通过申请的 `save_points.save_points` 原始值，而不是：

- `save_points.points`；
- 实际到账积分；
- `user_points.points`。

因此排行榜表示“用户原始存入量”，不表示实际到账积分。

## 33. 当前权限风险

这是当前实现最严重的风险之一。

### 33.1 没有员工身份检查

`audit` 不检查：

```text
user_type == staff
```

### 33.2 没有门店绑定检查

`audit` 不检查审核人是否有 `store_id`。

### 33.3 没有门店数据范围检查

`audit` 不检查：

```text
save_points.store_id == 当前员工.store_id
```

### 33.4 审核人字段可能记录普通用户

`verify_staff` 直接写入当前认证用户 ID。

如果普通顾客调用接口，其用户 ID 也可能被记录为审核员工。

## 34. 当前重复审核与幂等风险

当前方法不要求申请原状态为 `1`。

因此同一申请可以重复提交：

```text
type = 2
```

每次都可能：

- 再次增加用户积分；
- 再次创建 `user_points`；
- 再次创建积分流水；
- 再次增加金币；
- 再次创建金币流水。

### 34.1 重复点击

员工前端重复点击审核通过，可能造成重复发放。

### 34.2 客户端超时重试

第一次请求已经提交但客户端没有收到响应，客户端重试会再次发放。

### 34.3 并发审核

两个员工同时审核同一申请时：

- 两边都可能读到同一申请；
- 没有申请行锁；
- 没有 `status = 1` 的条件更新；
- 两边都可能发放资产。

### 34.4 通过后再拒绝

已通过并发放资产的申请，之后可以再次调用 `type = 3` 改成拒绝。

系统不会自动追回：

- 已发积分；
- 已发金币；
- 已建流水。

最后会出现：

```text
申请状态为拒绝，但用户已经收到资产
```

### 34.5 拒绝后再通过

已经拒绝的申请也可以再次改成通过并发放资产。

当前没有审核状态机约束。

---

## 35. 当前并发与余额快照风险

### 35.1 用户没有加行锁

用户积分和余额的增量更新本身通常是原子的，但：

- 变更前余额通过普通查询取得；
- 增量更新后再通过普通查询取得变更后余额；
- 中间可能混入其他并发交易。

因此流水中的：

- `balance_before`；
- `balance_after`；

不一定只反映本次审核造成的变化。

### 35.2 基数计算没有锁

计算基数时：

- 上一次存分可能被其他事务修改；
- 新取分记录可能同时创建；
- 其他审核可能同时提交。

本次计算没有保存查询快照，也没有对相关记录加锁。

---

## 36. 当前时间与规则风险

### 36.1 审核时间决定结果

申请提交时间相同，只要审核时间不同，结果可能不同。

例如：

- 09:59 审核进入营业规则；
- 10:00 审核进入标准规则；
- 16:59 审核进入标准规则；
- 17:00 审核重新进入营业规则。

### 36.2 审核积压

用户在营业时段提交，但员工次日中午才审核，将按非营业时间规则处理。

### 36.3 服务器时区

计算使用应用服务器的 `Carbon::now()`。

如果服务器或应用时区设置错误，营业时段判断会整体偏移。

### 36.4 `updated_at` 可被其他修改影响

未来如果其他功能修改已审核申请，`updated_at` 会变化。

下一次基数计算可能把该修改时间误认为上一次审核通过时间。

系统虽然有专门的 `verify_time`，但基数查询没有使用它。

---

## 37. 当前数值与精度风险

### 37.1 积分除法

积分除以 5 后通过整数转换截断小数。

正数场景等价于向下取整。

### 37.2 金币除法

金币除以 2000，保留两位小数并截断，不进行四舍五入。

### 37.3 金币比较精度

`bccomp` 没有指定 scale，结果依赖全局 BCMath 配置。

### 37.4 余额更新参数是整数

金币是两位小数，但余额增量方法接收整数，可能丢失小数。

### 37.5 流水金额与余额变化不一致

可能出现：

```text
金币流水 amount = 2.50
用户 balance 实际只增加 2.00
```

### 37.6 积分流水金额与积分变化不一致

积分综合流水 `amount` 使用原始积分，账户变化使用实际积分。

## 39. 不应原样迁移的问题清单

在其他系统重新实现时，不应直接复制以下行为：

1. 审核接口只验证 JWT，不验证员工身份；
2. 不验证员工所属门店；
3. 不限制申请门店；
4. 不验证申请必须处于待审核状态；
5. 不限制 `type` 只能为 2 或 3；
6. 允许同一申请重复通过并重复发资产；
7. 允许通过后改拒绝但不追回资产；
8. 没有申请行锁和条件更新；
9. 找不到申请时没有显式回滚；
10. 状态更新失败时没有显式回滚；
11. 缺少正式请求参数验证；
12. 审核计算使用当前审核时间而没有冻结业务时间；
13. 基数统计跨门店；
14. 上一次存分查询跨门店；
15. 使用 `updated_at` 代替专用审核通过时间；
16. `businessEnd` 未进入数据库查询条件；
17. 实际计算和描述生成重复查询；
18. 计算结果没有写回申请；
19. `save_points.points` 与实际到账可能不一致；
20. 积分流水 amount 与真实积分变化不一致；
21. 金币注释写 `/1000`，实际为 `/2000`；
22. 金币比较精度依赖全局配置；
23. 金币是小数但余额增量参数为整数；
24. 金币流水与真实余额变化可能不一致；
25. 综合交易流水保存结果未检查；
26. `user_points` 没有 `source_id`；
27. 只更新 `users.points`，不更新其他积分账户字段；
28. 没有规则版本和结构化计算快照；
29. 拒绝没有原因；
30. 成功响应不返回任何计算结果。

## 40. 推荐的新系统业务规则确认项

在重新实现之前，业务方必须明确以下问题。

### 40.1 审核业务时间

实际计算应以哪个时间为准：

- 用户提交申请时间；
- 员工审核时间；
- 用户实际发生业务的时间；
- 门店营业日；
- 人工指定时间。

不建议让审核排队速度影响用户最终权益。

### 40.2 基数是否跨门店

需要明确：

- 基数按用户全局累计；
- 还是按用户加门店分别累计。

### 40.3 `S <= B` 时的规则

当前代码是：

```text
全部按1:5到账
```

需要业务方确认是否正确。

也可能存在另一种业务理解：

```text
基数范围内全部按1:1到账
```

两种规则结果完全不同，不能仅根据“基数积分”名称推断。

### 40.4 金币除数

必须确认：

- `/1000`；
- 还是当前实际代码的 `/2000`。

### 40.5 金币是否允许小数

需要明确：

- 金币只允许整数；
- 允许两位小数；
- 小数向下取整；
- 四舍五入；
- 不足最小单位累计到下次。

### 40.6 基数是否可以部分消耗

当前规则在 `S <= B` 时不会记录剩余基数，也不会在下一次延续。

需要明确基数是：

- 一个时间窗口统计值；
- 还是可以逐次消耗的业务额度。

## 41. 推荐的新系统请求契约

建议请求至少包括：

| 参数 | 类型 | 规则 |
| --- | --- | --- |
| `application_id` | 正整数 | 必填，存分申请 ID |
| `decision` | 枚举 | `approve` 或 `reject` |
| `remark` | 字符串 | 拒绝时必填，通过时可选 |
| `version` | 整数 | 必填，用于乐观锁 |
| `idempotency_key` | 字符串 | 必填，防止客户端重试 |

审核人不应由请求传入，应从认证上下文取得。

门店不应由请求决定，应由申请和审核人权限共同验证。

## 42. 推荐的权限规则

审核开始前必须验证：

1. 当前用户已登录；
2. 当前用户状态正常；
3. 当前用户角色是员工或具备存分审核权限；
4. 当前员工绑定有效门店；
5. 存分申请存在；
6. 存分申请门店等于员工可管理门店；
7. 申请用户存在；
8. 申请状态为待审核；
9. 申请未被其他审核任务锁定或处理。

如果总部人员可以跨门店审核，应通过明确权限授权，而不是默认允许。

## 43. 推荐的事务与幂等流程

建议在一个数据库事务中执行：

```text
开始事务
-> 根据申请 ID 查询并锁定申请
-> 验证申请状态为 pending
-> 验证审核权限和门店范围
-> 验证幂等键未处理
-> 冻结本次计算时间和规则版本
-> 查询并锁定或快照基数相关数据
-> 计算 S、B、E、A、C
-> 锁定用户资产账户
-> 更新申请审核状态和计算快照
-> 增加积分
-> 写积分账本
-> 按规则增加金币
-> 写金币账本
-> 保存幂等结果
-> 提交事务
```

状态更新应使用条件更新：

```text
where id = application_id
and status = pending
and version = request.version
```

受影响行数必须等于 1。

否则应返回：

```text
该申请已被其他人员处理
```

## 44. 推荐保存的审核计算快照

建议为每次审核保存：

| 字段 | 说明 |
| --- | --- |
| `application_id` | 申请 ID |
| `decision` | 通过或拒绝 |
| `auditor_id` | 审核人 |
| `auditor_store_id` | 审核人门店 |
| `audited_at` | 审核时间 |
| `business_date` | 业务日期 |
| `business_start_at` | 营业开始 |
| `business_end_at` | 营业结束 |
| `calculation_start_at` | 基数统计起点 |
| `calculation_end_at` | 基数统计终点 |
| `last_approved_save_id` | 上一次通过申请 ID |
| `requested_points` | 原始积分 S |
| `base_points` | 基数积分 B |
| `excess_points` | 超出积分 E |
| `awarded_points` | 实际积分 A |
| `coin_base_points` | 金币计算使用的积分 |
| `calculated_coin` | 计算金币 C |
| `credited_coin` | 实际入账金币 |
| `rule_version` | 规则版本 |
| `rounding_mode` | 截断或四舍五入 |
| `remark` | 审核备注 |

这样历史记录才能准确复算和审计。

## 45. 推荐的统一资产账本

积分和金币都应使用不可变账本作为事实来源。

每笔账本至少保存：

- 用户 ID；
- 资产类型；
- 变更数量；
- 变更前余额；
- 变更后余额；
- 业务类型；
- 业务 ID；
- 唯一业务键；
- 规则版本；
- 操作人；
- 创建时间。

建议唯一业务键：

```text
save-points:{申请ID}:points
save-points:{申请ID}:balance
```

数据库建立唯一索引。

即使审核请求重复到达，也无法重复发放。

账本 `amount` 必须等于：

```text
balance_after - balance_before
```

原始申请积分应保存到单独字段，不应混用为资产变更金额。

## 46. 推荐的纯计算函数

建议把积分和金币计算实现为一个纯业务函数。

输入：

```text
审核业务时间
原始申请积分 S
基数积分 B
规则版本
```

输出：

```text
是否属于营业时段
营业日期
实际积分 A
超出积分 E
金币计算基数
计算金币 C
计算说明
```

计算函数不应：

- 自己查询数据库；
- 自己获取当前时间；
- 自己写日志；
- 自己更新用户；
- 在描述生成时重新计算。

所有后续记录和响应必须使用同一个计算结果对象。

## 47. 推荐的响应

审核通过后建议返回：

```text
申请 ID
审核状态
审核时间
审核人
原始申请积分 S
基数积分 B
超出积分 E
实际到账积分 A
获得金币 C
用户最新积分
用户最新余额
规则版本
```

审核拒绝后建议返回：

```text
申请 ID
审核状态
审核时间
审核人
拒绝原因
```

重复请求如果幂等键一致，应返回第一次处理结果，而不是再次发资产。

## 48. 推荐状态机

建议存分申请状态：

```text
pending
  -> approved

pending
  -> rejected

pending
  -> cancelled
```

终态：

- `approved`
- `rejected`
- `cancelled`

进入终态后不能直接改成其他状态。

如果需要纠错，应新增独立流程：

- 审核撤销；
- 资产冲正；
- 重新审核。

冲正必须创建反向账本，不能删除原流水。

## 49. 建议验收场景

### 49.1 权限

1. 未登录用户不能审核；
2. 普通顾客不能审核；
3. 没有门店的员工不能审核；
4. 员工不能审核其他门店申请；
5. 有跨门店权限的总部人员可以审核授权门店；
6. 审核人必须正确记录。

### 49.2 参数

1. 缺少申请 ID；
2. 申请 ID 不是正整数；
3. 申请不存在；
4. 缺少审核决定；
5. 审核决定不是通过或拒绝；
6. 拒绝时没有原因；
7. 乐观锁版本不一致；
8. 幂等键缺失；
9. 幂等键重复。

### 49.3 审核状态

1. 待审核申请可以通过；
2. 待审核申请可以拒绝；
3. 已通过申请不能再次通过；
4. 已通过申请不能直接拒绝；
5. 已拒绝申请不能再次通过；
6. 两个员工并发审核只有一个成功；
7. 客户端超时重试不重复发资产。

### 49.4 营业时间

1. 09:59:59 属于营业时段；
2. 10:00:00 属于非营业时段；
3. 16:59:59 属于非营业时段；
4. 17:00:00 属于营业时段；
5. 00:00 属于前一天营业时段；
6. 跨月时营业日期正确；
7. 跨年时营业日期正确；
8. 应用时区为 Asia/Shanghai。

### 49.5 基数积分

1. 本营业时段没有上次存分；
2. 本营业时段存在上次存分；
3. 上次存分之前的取分不重复计入；
4. 上次存分之后的取分正确计入；
5. 待审核取分不计入；
6. 已拒绝取分不计入；
7. 已批准取分计入；
8. 起点时间的记录是否包含符合业务预期；
9. 终点时间的记录是否排除符合业务预期；
10. 跨门店记录按确认后的规则处理。

### 49.6 实际积分

1. 非营业时间使用五分之一；
2. 营业时间基数为零使用五分之一；
3. `S < B`；
4. `S = B`；
5. `S > B`；
6. `S-B` 不能被5整除；
7. 大额积分不溢出；
8. 实际积分与申请快照一致；
9. 账户变化与积分账本 amount 一致。

### 49.7 金币

1. 确认使用 `/1000` 或 `/2000`；
2. 确认是否允许小数；
3. 金币为 0；
4. 金币为 0.01；
5. 金币为 0.50；
6. 金币为 1.00；
7. 金币为 2.50；
8. 需要截断的三位以上小数；
9. 余额实际变化等于金币账本 amount；
10. 金币发放失败时整个审核事务回滚。

### 49.8 一致性

1. 积分账户更新失败；
2. 积分账本创建失败；
3. 余额账户更新失败；
4. 余额账本创建失败；
5. 任意一步失败后申请保持待审核；
6. 任意一步失败后不产生部分资产；
7. 审核成功后所有账本可按申请 ID 查询；
8. 审核计算快照可以完整复算结果。

## 50. 当前真实流程摘要

当前方法的真实执行逻辑可以概括为：

```text
小程序用户提交 id 和 type
-> 系统开始事务
-> 只按 id 查询存分申请
-> 无条件把申请状态改为 type
-> 记录当前登录用户为审核人
-> type 不等于2时直接提交
-> type 等于2时根据审核当前时间判断营业时段
-> 查找本时段上一次已通过存分
-> 汇总此后已批准取分作为基数
-> 按1:5或“基数1:1、超出1:5”计算实际积分
-> 增加 users.points
-> 写 user_points
-> 写积分 transaction_records
-> 按原始积分或超出积分除以2000计算金币
-> 金币大于0时增加 users.balance
-> 写余额 transaction_records
-> 提交事务
-> 返回空数据和“审核成功”
```

## 51. 新系统必须保证的关键结果

需要迁移的是存分审核的业务能力，而不是当前方法的代码结构。

新系统至少必须保证：

- 只有授权员工可以审核；
- 员工只能审核授权门店数据；
- 请求参数具有正式验证；
- 申请只能从待审核进入一个终态；
- 同一申请不能重复发放；
- 并发审核只有一个成功；
- 计算业务时间被明确冻结；
- 基数统计规则有明确门店范围；
- 积分和金币公式有版本；
- `/1000` 或 `/2000` 得到业务确认；
- 金币精度和舍入方式明确；
- 实际积分回写申请快照；
- 账本 amount 与真实账户变化一致；
- 积分和余额在同一个事务中更新；
- 所有计算输入和输出可审计；
- 失败时不产生部分成功；
- 历史审核可以完整复算；
- 纠错通过冲正完成，不直接改写历史资产事实。
