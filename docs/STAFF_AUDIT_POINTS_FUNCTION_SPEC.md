# 员工审核存入积分功能规格说明

## 1. 功能范围

用户在小程序提交存积分申请，工作人员在绑定门店内审核。审核通过后只增加会员积分；审核驳回不改变任何会员资产。

本流程包含：

- 用户提交存积分申请；
- 门店范围内的待审核列表和详情；
- 工作人员通过或驳回；
- 按营业时段和取分基数计算实际到账积分；
- 写入积分账户和不可变积分流水；
- 保存审核人、规则版本和计算快照。

## 2. 路由

用户提交：

```text
POST /api/v2/mini/point-savings
```

工作人员查询与审核：

```text
GET  /api/v2/mini/staff/point-savings
GET  /api/v2/mini/staff/point-savings/{requestID}
POST /api/v2/mini/staff/point-savings/{requestID}/review
```

门店后台查询与审核：

```text
GET  /api/v2/store/point-savings
GET  /api/v2/store/point-savings/{requestID}
POST /api/v2/store/point-savings/{requestID}/review
```

写接口必须携带 `Idempotency-Key`。工作人员和门店后台的门店范围来自登录令牌，不接受客户端覆盖。

## 3. 申请创建

请求体：

```json
{
  "amount": 1000,
  "storeId": 1
}
```

约束：

- `amount` 必须是 `1` 至 `1,000,000,000` 的整数；
- `storeId` 必须对应启用中的门店；
- 重复使用同一幂等键时返回同一申请；
- 创建后状态为 `pending`；
- 创建申请时不改变会员积分余额。

## 4. 审核状态

| 状态 | 含义 |
| --- | --- |
| `pending` | 待审核 |
| `approved` | 已通过并完成积分入账 |
| `rejected` | 已驳回，未发生资产变化 |

审核接口只接受 `approve` 或 `reject`。已处理申请不得再次审核。

## 5. 基数积分

审核发生在门店当前营业时段内时，基数积分为以下时间区间内该会员所有已通过取分记录之和：

```text
当前营业时段开始时间，或本时段内上一次存分审核通过时间
到本次审核时间
```

非营业时段不计算基数，按标准比例处理。

## 6. 实际到账积分

设：

- `S`：申请存入积分；
- `B`：基数积分；
- `D`：标准折算除数，默认 `5`；
- `L`：低于基数折算除数，默认 `2`。

计算规则：

| 场景 | 实际到账积分 |
| --- | ---: |
| 非营业时段 | `floor(S / D)` |
| 营业时段且 `B <= 0` | `floor(S / D)` |
| 营业时段且 `S < B` | `floor(S / L)` |
| 营业时段且 `S = B` | `S` |
| 营业时段且 `S > B` | `B + floor((S - B) / D)` |

所有除法结果均向下取整。比例由总后台统一配置，配置更新只影响更新后执行的审核。

## 7. 审核事务

审核通过必须在一个数据库事务内完成：

1. 按申请 ID 和门店 ID 锁定待审核申请；
2. 校验申请仍为 `pending`；
3. 读取门店营业时间和当前规则；
4. 计算基数及实际到账积分；
5. 锁定或创建会员积分账户；
6. 增加积分余额并写入积分流水；
7. 更新申请状态和计算快照；
8. 提交事务。

任何一步失败都必须回滚，不允许只更新申请状态或只更新积分余额。

审核驳回只更新申请状态、备注、审核人快照和审核时间。

## 8. 审核快照

审核通过后保存：

- 原始存入积分；
- 基数积分；
- 超出基数积分；
- 实际到账积分；
- 规则版本及两个积分折算除数；
- 营业日期和营业时间范围；
- 基数统计起止时间；
- 上一次审核通过的申请 ID；
- 计算说明；
- 审核人类型、ID 和身份快照；
- 审核时间。

历史审核记录使用保存时的快照展示，不使用最新规则覆盖。

## 9. 验收重点

- 用户重复提交不会创建重复申请；
- 工作人员只能审核绑定门店的申请；
- 并发审核同一申请只允许一次成功；
- 驳回不产生积分流水；
- 通过只产生积分资产变动；
- 审核结果与保存的规则版本、基数和计算说明一致；
- 跨午夜营业时间能够得到正确的业务日期与时间窗口；
- 门店营业时间配置无效时禁止审核通过；
- 历史记录不会暴露已下线的资产发放逻辑。
