# 餐品下单功能规格说明

## 1. 文档目的

本文整理小程序餐品下单方法 `FoodOrderController::addOrder` 的实际业务行为。

本文不是源代码说明或代码迁移指南，而是一份脱离具体编程语言、可用于其他系统重新实现的业务规格。内容包括：

- 接口输入与输出；
- 商品、金额、库存和积分计算规则；
- 订单及订单明细创建规则；
- 微信支付和金币支付流程；
- 支付成功后的积分、酒券和打印处理；
- 数据变更范围；
- 失败和事务处理；
- 当前实现存在的风险；
- 新系统实现时建议采用的标准流程。

原始实现位置：

- `app/Http/Controllers/Api/Mini/FoodOrderController.php`
- 方法起始位置：第 54 行

---

## 2. 功能概述

该功能供小程序登录用户创建餐品订单，支持一个订单包含多种商品，每种商品可以购买多份。

系统支持两种支付方式：

1. 微信支付：创建待支付订单和微信预支付单，返回小程序支付参数；用户实际支付成功后，由微信支付回调完成积分、酒券和打印。
2. 金币支付：直接使用用户的 `balance` 余额付款；余额扣除成功后，订单立即进入备餐状态，并继续处理积分、酒券和打印。

该功能实际包含以下业务能力：

1. 身份认证；
2. 请求参数验证；
3. 门店、桌位和座位存在性验证；
4. 商品有效性验证；
5. 商品库存验证；
6. 订单金额计算；
7. 商品赠送积分计算；
8. 订单主记录创建；
9. 订单商品明细创建；
10. 商品库存扣减；
11. 微信或金币支付处理；
12. 用户积分发放；
13. 酒券发放；
14. 酒券过期任务创建；
15. 用户收支记录创建；
16. 门店小票打印；
17. 业务日志记录。

## 3. 接口入口

### 3.1 请求信息

- 请求方式：`POST`
- 请求地址：`/api/mini/food/add`
- 客户端：微信小程序
- 认证方式：JWT
- 认证中间件：`miniprogram.jwt`
- 用户认证 Guard：`api`

### 3.2 认证要求

请求进入下单方法之前，认证中间件需要完成：

1. 从请求中解析 JWT；
2. 验证 Token 是否有效、是否过期；
3. 根据 Token 取得用户；
4. 确认用户状态为空或 `active`；
5. 将当前请求的默认认证 Guard 设置为 `api`；
6. 将认证用户绑定到当前请求。

认证失败时，不进入下单流程。

可能返回的认证失败消息包括：

- 用户不存在；
- 用户账户已被禁用；
- 登录已过期，请重新登录；
- 登录令牌无效；
- 请先登录。

## 4. 请求参数

| 参数 | 必填 | 类型 | 说明 |
| --- | --- | --- | --- |
| `goods` | 是 | 数组 | 本次订单的商品列表，至少包含一项 |
| `goods[].id` | 是 | 正整数 | 商品 ID |
| `goods[].count` | 是 | 正整数 | 购买数量，最小值为 1 |
| `pay_type` | 是 | 整数 | 支付方式：`1` 为微信支付，`2` 为金币支付 |
| `store_id` | 是 | 正整数 | 下单门店 ID |
| `table_id` | 否 | 整数或空 | 就餐桌位 ID |
| `seat_id` | 否 | 整数或空 | 就餐座位 ID |

概念请求示例：

```text
门店：1
桌位：10
座位：可选
支付方式：微信或金币
商品：
  - 商品25，购买2份
  - 商品31，购买1份
```

### 4.1 参数验证规则

系统按照以下规则验证请求：

1. `goods` 必须存在；
2. `goods` 必须是数组；
3. `goods` 至少包含一个商品；
4. 每项商品必须包含 `id`；
5. 商品 ID 必须是大于或等于 1 的整数；
6. 每项商品必须包含 `count`；
7. 商品数量必须是大于或等于 1 的整数；
8. `pay_type` 必须存在；
9. `pay_type` 必须是整数；
10. `pay_type` 只能是 1 或 2；
11. `store_id` 必须存在；
12. `store_id` 必须对应一个已存在的门店；
13. `table_id` 可以为空，填写时必须对应一个已存在的桌位；
14. `seat_id` 可以为空，填写时必须对应一个已存在的座位。

### 4.2 当前验证范围的限制

当前实现只验证桌位和座位是否存在，没有验证：

- 桌位是否属于请求中的门店；
- 座位是否属于请求中的门店；
- 座位是否属于请求中的桌位；
- 桌位或座位当前是否可用；
- 桌位或座位是否已被其他预约占用。

### 4.3 参数验证失败响应

参数验证失败时：

- HTTP 状态码仍然是 `200`；
- 业务 `code` 为 `422`；
- `message` 为“参数验证失败”；
- `data` 为各字段的验证错误详情。

响应概念结构：

```text
code: 422
message: 参数验证失败
data: 字段验证错误集合
```

## 5. 用户与门店信息

参数验证通过后，系统根据 `store_id` 查询门店，用于后续取得门店名称并打印小票。

进入事务后，系统从 `api` Guard 取得当前登录用户。

用户信息至少会在后续流程中用于：

- 写入订单的 `user_id`；
- 取得微信支付需要的 `openid`；
- 金币支付时扣减余额；
- 支付成功后增加积分；
- 发放酒券；
- 小票显示昵称或脱敏手机号；
- 写入业务日志和交易记录。

如果下单方法中无法取得当前用户，则返回“用户未登录”。

---

## 6. 数据库事务范围

用户验证通过后，系统手动开始数据库事务。

事务中的主要操作包括：

1. 校验商品；
2. 计算金额和积分；
3. 创建订单；
4. 创建订单明细；
5. 扣减库存；
6. 创建微信预支付单或执行金币扣款；
7. 更新金币订单支付状态。

微信支付与金币支付的事务提交时机不同：

- 微信支付：微信预支付单创建成功后提交事务；
- 金币支付：余额扣除且订单状态更新成功后提交事务。

金币支付的积分、酒券、交易流水和打印发生在事务提交之后。

微信支付的积分、酒券和打印发生在支付回调的另一个事务中。

---

## 7. 商品校验

系统逐项处理 `goods` 中的商品。

每项商品必须同时满足：

1. 商品 ID 存在；
2. 商品的 `store_id` 等于请求中的 `store_id`；
3. 商品状态为 `active`；
4. 商品库存大于或等于本次购买数量。

### 7.1 商品不存在或已下架

以下情况都按商品无效处理：

- 商品 ID 不存在；
- 商品不属于指定门店；
- 商品状态不是 `active`。

系统将：

1. 回滚事务；
2. 返回“餐品ID {商品ID} 不存在或已下架”。

### 7.2 库存不足

如果商品当前库存小于购买数量，系统将：

1. 回滚事务；
2. 返回“餐品 {商品名称} 库存不足”。

## 8. 金额计算

所有价格以服务器查询到的商品当前价格为准，客户端不提交也不能决定实际结算价格。

每项商品小计：

```text
商品小计 = 商品当前价格 × 购买数量
```

订单总金额：

```text
订单总金额 = 所有商品小计之和
```

计算结果用于：

- 写入订单总金额；
- 写入每项订单明细小计；
- 微信支付金额；
- 金币余额扣除金额；
- 交易记录金额；
- 小票订单合计。

当前实现使用 PHP 数值运算计算金额，微信支付时再将订单金额乘以 100 并转换为整数分。

---

## 9. 赠送积分计算

每个商品可以配置 `points`。

只要商品的 `points` 大于零，购买后就赠送积分。

每项商品赠送积分：

```text
商品赠送积分 = 商品 points × 购买数量
```

订单赠送积分：

```text
订单赠送积分 = 所有商品赠送积分之和
```

积分是商品配置规则，不是按照订单金额换算。

当前计算采用 0 位小数，因此积分按整数处理。

---

## 10. 商品快照

商品校验完成后，系统在内存中为每项商品整理以下信息：

| 字段 | 说明 |
| --- | --- |
| `product_id` | 商品 ID |
| `product_name` | 下单时商品名称 |
| `product_price` | 下单时商品单价 |
| `product_type` | 下单时商品类型 |
| `product_points` | 下单时商品配置的积分 |
| `quantity` | 购买数量 |
| `subtotal` | 商品小计 |

其中：

- 商品名称和价格是历史订单展示与结算所需快照；
- 商品类型用于判断是否需要发酒券；
- 商品积分用于计算支付成功后的赠送积分和用户券信息。

### 10.1 当前持久化差异

当前 `FoodOrderItem` 模型允许批量写入：

- `food_order_id`
- `category_id`
- `product_id`
- `product_name`
- `product_price`
- `quantity`
- `subtotal`

但没有允许批量写入 `product_type` 和 `product_points`。

因此当前实际结果是：

- `product_name` 和 `product_price` 会保存为订单快照；
- `product_type` 可能使用数据库默认值，而不是商品真实类型；
- `product_points` 没有保存到订单明细；
- 金币支付仍能使用内存中的商品类型和积分；
- 微信支付回调会重新关联商品表读取当前类型和当前积分。

## 11. 订单号生成

订单号组成规则：

```text
FO + 年月日时分秒 + 四位随机数
```

示例：

```text
FO202607251530429381
```

订单号用于：

- 本地订单唯一标识；
- 微信支付商户订单号；
- 微信支付回调查找订单；
- 用户酒券来源订单号；
- 日志记录；
- 小票展示；
- 余额消费描述。

数据库对订单号设置唯一索引，但当前生成流程没有在发生唯一键冲突时自动重新生成和重试。

---

## 12. 创建订单主记录

订单创建时写入以下信息：

| 字段 | 初始值 |
| --- | --- |
| `order_no` | 新生成的订单号 |
| `user_id` | 当前登录用户 ID |
| `store_id` | 请求中的门店 ID |
| `table_id` | 请求中的桌位 ID，可以为空 |
| `total_amount` | 计算出的订单总金额 |
| `payment_method` | 微信为 `wechat`，金币为 `coin` |
| `payment_status` | `pending` |
| `order_status` | `pending` |

创建时没有写入：

- `seat_id`；
- `points_earned`；
- `transaction_id`；
- `paid_at`。

虽然 `seat_id` 已经从请求中读取并验证，但没有放入订单创建数据。

---

## 13. 创建订单明细

主订单创建后，系统为每项商品创建一条订单明细。

每条明细通过 `food_order_id` 关联主订单，主要保存：

- 商品 ID；
- 下单时商品名称；
- 下单时商品单价；
- 购买数量；
- 商品小计。

一个订单可以包含多条订单明细。

订单明细与订单主记录存在级联关系，删除订单时，相应订单明细也会被删除。

---

## 14. 扣减库存

订单和明细创建完成后，系统再次遍历请求商品，执行库存扣减。

库存变更规则：

```text
商品新库存 = 商品原库存 - 购买数量
```

库存扣减发生在实际支付完成之前。

因此：

- 金币支付失败且事务成功回滚时，库存恢复；
- 微信预支付创建失败且事务成功回滚时，库存恢复；
- 微信预支付创建成功后，订单即使一直未付款，库存仍然已经扣除；
- 当前流程没有未支付订单超时关闭和恢复库存的机制。

---

## 15. 微信支付流程

当 `pay_type = 1` 时，系统执行微信支付分支。

### 15.1 微信支付请求信息

系统向微信支付服务提交：

| 字段 | 内容 |
| --- | --- |
| 商户订单号 | 本地订单号 |
| 支付描述 | `餐品订单 - 本地订单ID` |
| 支付金额 | 订单金额乘以 100 后转换为整数分 |
| 币种 | 人民币 |
| 付款用户 | 当前用户的 `openid` |
| 支付回调地址 | `/api/mini/food-order/notify` |

微信支付服务调用 JSAPI 下单接口并取得 `prepay_id`，随后生成小程序调起微信支付所需参数。

### 15.2 微信预支付创建成功

微信预支付单创建成功后，系统：

1. 提交本地数据库事务；
2. 保留订单主记录；
3. 保留订单明细；
4. 保留库存扣减；
5. 写入微信支付发起成功日志；
6. 将小程序支付参数返回给客户端。

此时订单状态仍然是：

| 字段 | 值 |
| --- | --- |
| `payment_status` | `pending` |
| `order_status` | `pending` |

返回数据包括：

| 字段 | 说明 |
| --- | --- |
| `order_id` | 本地订单 ID |
| `order_no` | 商户订单号 |
| `total_fee` | 订单总金额 |
| `payment_status` | 当前支付状态，通常为 `pending` |
| `pay_params` | 小程序调起微信支付的参数 |

成功消息：

```text
订单创建成功，请完成支付
```

### 15.3 微信预支付创建失败

如果微信支付服务抛出异常，系统：

1. 回滚数据库事务；
2. 删除本事务中创建的订单和明细；
3. 恢复本事务中扣减的库存；
4. 写入微信支付发起失败日志；
5. 返回“支付发起失败：具体异常信息”。

需要注意，微信支付属于外部系统。存在微信端已经创建预支付单、但本地因网络或提交失败而回滚的可能性。

---

## 16. 微信支付回调流程

微信支付订单的积分、酒券和打印不是在创建订单时执行，而是在支付成功回调中执行。

回调地址：

```text
/api/mini/food-order/notify
```

该地址不要求小程序 JWT 认证。

### 16.1 回调数据处理

微信支付服务会：

1. 读取原始请求体和请求头；
2. 解析 JSON；
3. 取得加密的 `resource`；
4. 使用微信支付 APIv3 密钥执行 AES-256-GCM 解密；
5. 提取商户订单号；
6. 提取微信交易号；
7. 提取支付金额；
8. 调用餐品订单回调业务。

### 16.2 查找和校验订单

业务回调根据商户订单号查找本地餐品订单。

处理规则：

1. 订单不存在时抛出“餐品订单不存在”；
2. 订单已经支付时直接返回成功；
3. 订单支付方式不是 `wechat` 时抛出“订单支付方式不匹配”。

### 16.3 支付金额校验现状

代码中原本存在以下校验意图：

```text
微信实付金额（分）应等于订单总金额（元）×100
```

但是当前金额比较逻辑已被注释，实际没有校验微信回调金额是否等于订单金额。

### 16.4 更新微信订单状态

回调业务开始事务后，将订单更新为：

| 字段 | 新值 |
| --- | --- |
| `payment_status` | `paid` |
| `order_status` | `preparing` |
| `transaction_id` | 微信支付交易号 |
| `paid_at` | 当前时间 |

### 16.5 重新读取商品信息

微信回调通过订单明细关联当前 `products` 表，重新取得：

- 当前商品名称；
- 当前商品价格；
- 当前商品类型；
- 当前商品积分。

然后根据这些当前值计算积分和发放酒券。

这意味着微信回调没有完整使用下单时的商品快照。

如果商品在下单后、支付前发生以下变化，支付结果可能被影响：

- 商品改名；
- 商品改价；
- 商品类型改变；
- 商品赠送积分改变；
- 商品被删除。

### 16.6 微信支付赠送积分

系统重新计算所有订单商品的赠送积分。

如果总积分大于零：

1. 查询用户积分变更前信息；
2. 增加用户 `points`；
3. 查询用户积分变更后信息；
4. 创建一条积分类型的 `transaction_records`；
5. 记录积分赠送成功日志。

积分交易记录内容：

| 字段 | 内容 |
| --- | --- |
| `amount_type` | `points` |
| `trans_type` | `1`，表示收入 |
| `amount` | 赠送积分 |
| `balance_before` | 增加前积分 |
| `balance_after` | 增加后积分 |
| `description` | 用户购买商品赠送积分 |
| `related_id` | 餐品订单 ID |

积分增加失败时只记录日志，回调不会因为积分失败主动抛出异常。

### 16.7 微信支付发放酒券

对于当前商品类型为 `2` 的订单商品：

1. 计算当前时间30天后的过期时间；
2. 按购买数量循环；
3. 每购买一份创建一张独立酒券；
4. 酒券初始状态为可使用；
5. 发券成功后创建一个30天延时的过期任务。

发券失败时记录错误日志，不主动抛出异常。

### 16.8 微信支付打印

完成积分和酒券处理后，系统取得用户和门店信息，生成订单小票并同步发送到打印机。

之后提交支付回调事务。

### 16.9 回调返回

处理成功时向微信返回：

```text
code: SUCCESS
message: 成功
```

处理失败时：

1. 回滚支付回调事务；
2. 写入错误日志和调用堆栈；
3. 返回 HTTP 500；
4. 返回 `FAIL`，微信支付平台可以继续重试回调。

---

## 17. 金币支付流程

当 `pay_type = 2` 时，系统执行金币支付。

业务中的“金币”实际对应用户表的 `balance` 字段。

### 17.1 读取扣款前余额

系统在扣款前读取一次用户信息，用于后续生成余额收支记录中的 `balance_before`。

### 17.2 锁定用户并校验余额

余额消费服务会：

1. 根据用户 ID 查询用户；
2. 对用户数据加排他行锁；
3. 检查用户是否存在；
4. 检查用户 `balance` 是否足够支付订单金额。

余额不足时抛出错误：

```text
余额不足，当前余额：{当前余额}，需要消费：{订单金额}
```

### 17.3 扣除余额

余额充足时：

```text
扣款后余额 = 扣款前余额 - 订单金额
```

系统更新用户的 `balance`。

### 17.4 创建余额消费明细

扣款成功后，系统创建 `balance_consumption_records`：

| 字段 | 内容 |
| --- | --- |
| `user_id` | 当前用户 ID |
| `amount_consumed` | 订单金额 |
| `balance_before` | 扣款前余额 |
| `balance_after` | 扣款后余额 |
| `consumption_type` | `order` |
| `related_type` | 餐品订单模型类型 |
| `related_id` | 餐品订单 ID |
| `description` | 餐品订单金币支付及订单号 |

### 17.5 更新金币订单状态

金币扣款成功后，订单更新为：

| 字段 | 新值 |
| --- | --- |
| `payment_status` | `paid` |
| `order_status` | `preparing` |

当前金币支付没有填写：

- `transaction_id`；
- `paid_at`。

### 17.6 提交事务

余额扣除和订单状态更新完成后，系统提交数据库事务。

事务提交后，以下结果已经不可通过当前事务回滚：

- 订单已经创建；
- 订单明细已经创建；
- 商品库存已经扣减；
- 用户余额已经扣除；
- 余额消费记录已经创建；
- 订单已经标记为已支付。

---

## 18. 金币支付后的积分处理

金币事务提交后，如果订单赠送积分大于零：

1. 增加用户 `points`；
2. 写入积分赠送成功日志。

如果积分更新失败：

- 接口返回“发放积分失败，请联系前台”；
- 但订单已经支付；
- 余额已经扣除；
- 库存已经扣除；
- 前面的数据库操作不会恢复。

金币支付的积分发放没有创建积分类型的 `transaction_records`，与微信支付行为不一致。

---

## 19. 酒券发放

商品的 `type = 2` 时，该商品被视为酒券类型商品。

金币支付和微信支付成功后都会发放酒券。

### 19.1 发券数量

```text
发券数量 = 酒券商品购买数量
```

例如：

- 购买1份酒券商品，创建1张用户券；
- 购买3份酒券商品，创建3张独立用户券。

### 19.2 用户券信息

每张用户券保存：

| 字段 | 内容 |
| --- | --- |
| `user_id` | 购买用户 |
| `product_id` | 来源商品 |
| `order_no` | 来源餐品订单号 |
| `name` | 商品名称 |
| `description` | `购买酒券产品获得` |
| `price` | 商品价格 |
| `points` | 商品积分 |
| `expired_time` | 发券时间30天后 |
| `status` | `1`，表示可使用 |

### 19.3 过期任务

每张酒券创建成功后，系统向 `coupon` 队列投递一个延时任务。

任务延时：

```text
30天
```

任务执行时：

1. 查询酒券；
2. 酒券不存在时只记录警告；
3. 酒券状态不是 `2` 时，将状态改成 `3`，表示已过期；
4. 酒券状态为 `2` 时，表示已经使用，不再修改。

### 19.4 发券失败处理

单张酒券创建失败时：

- 写入错误日志；
- 不回滚订单；
- 不恢复余额；
- 不恢复库存；
- 继续处理其他酒券。

---

## 20. 金币余额收支记录

金币支付完成后，系统再次读取用户信息，取得扣款后余额。

随后向 `transaction_records` 创建一条余额支出记录：

| 字段 | 内容 |
| --- | --- |
| `user_id` | 当前用户 ID |
| `amount_type` | `balance` |
| `trans_type` | `2`，表示支出 |
| `amount` | 订单总金额 |
| `balance_before` | 扣款前余额 |
| `balance_after` | 扣款后余额 |
| `description` | `用户点餐扣除金币:{订单金额}` |
| `related_id` | 餐品订单 ID |

因此一次金币支付目前会创建两套余额记录：

1. `balance_consumption_records`；
2. `transaction_records`。

## 21. 小票打印

金币支付完成后立即打印小票。

微信支付在支付成功回调中打印小票。

### 21.1 用户信息显示

系统优先使用用户手机号：

- 手机号存在且长度正常时，保留前3位和后4位；
- 中间替换为4个星号；
- 示例：`138****5678`。

用户没有手机号时，使用用户昵称。

### 21.2 小票内容

小票依次包含：

1. 图片或 Logo 指令；
2. `InwardClub` 标题；
3. 门店名称；
4. 订单号；
5. 当前打印时间；
6. 用户脱敏手机号或昵称；
7. 本单赠送积分；
8. 商品表头；
9. 每项商品名称；
10. 每项商品购买数量；
11. 每项商品金额；
12. 订单总金额；
13. “谢谢惠顾”；
14. 切纸指令。

### 21.3 打印设备范围

当前实现查询所有 `status = 1` 的打印设备。

系统会向每台启用的设备各发送一份小票，参数包括：

- 打印机序列号；
- 小票内容；
- 打印份数 1；
- 打印机语音配置。

当前查询没有按照订单门店过滤打印机。

### 21.4 打印结果

打印成功或失败都会记录日志。

正常情况下，打印失败不会撤销订单、余额、积分或酒券。

打印请求属于同步外部网络调用，会占用当前请求或回调的执行时间。

## 22. 订单状态变化

| 业务阶段 | `payment_status` | `order_status` |
| --- | --- | --- |
| 订单刚创建 | `pending` | `pending` |
| 微信预支付创建成功 | `pending` | `pending` |
| 微信支付回调成功 | `paid` | `preparing` |
| 金币支付成功 | `paid` | `preparing` |

该方法及支付回调不会将订单推进到：

- `ready`：待取餐；
- `completed`：已完成；
- `cancelled`：已取消；
- `refunded`：已退款。

后续状态需要由其他后台、出餐或退款流程处理。

## 27. 当前实现的事务一致性

### 27.1 微信支付创建阶段

本地订单、明细和库存处于同一个数据库事务。

微信预支付创建成功后才提交本地事务。

主要问题是微信支付属于事务外部的远程系统，无法和本地数据库形成真正的原子事务。

可能出现：

- 微信预支付单已创建，但本地提交失败；
- 本地请求超时，但微信端已经受理；
- 本地订单存在，但用户一直未完成支付；
- 库存已扣除但没有超时释放。

### 27.2 金币支付阶段

以下操作基本处于同一个事务：

- 创建订单；
- 创建明细；
- 扣减库存；
- 锁定用户；
- 扣减余额；
- 创建余额消费记录；
- 更新订单为已支付。

以下操作发生在提交之后：

- 增加积分；
- 发放酒券；
- 投递酒券过期任务；
- 创建 `transaction_records`；
- 打印小票。

因此可能出现部分成功：

- 订单和扣款成功，但积分失败；
- 订单和扣款成功，但酒券部分失败；
- 订单和扣款成功，但交易流水创建失败；
- 订单和扣款成功，但打印失败；
- 接口返回失败，但用户实际上已经完成支付。

### 27.3 微信支付回调阶段

订单状态、积分、用户券和打印被放在支付回调处理流程中。

但是：

- 普通幂等判断发生在事务和行锁之外；
- 并发回调可能同时判断订单未支付；
- 外部打印请求发生在事务提交前；
- 商品信息读取的是当前商品表而不是完整订单快照。

## 28. 当前实现中不应原样迁移的问题

在其他系统重新实现时，应保留业务目标，但不应直接复制以下行为。

### 28.1 参数与门店范围

1. `seat_id` 被读取和验证，但没有保存；
2. 桌位没有验证是否属于门店；
3. 座位没有验证是否属于门店；
4. 座位没有验证是否属于桌位；
5. 没有验证桌位、座位是否可用或被预约。

### 28.2 库存

1. 商品库存读取时没有加行锁；
2. 校验库存和扣减库存不是带条件的原子操作；
3. 并发订单可能同时通过库存校验并造成超卖；
4. 同一商品在请求中重复出现时，各项会独立校验；
5. 重复商品的合计购买量可能超过库存并扣成负数；
6. 微信订单未支付时没有释放库存。

### 28.3 金额

1. 金额使用浮点数进行乘法和加法；
2. 微信支付金额通过乘以 100 后直接转换整数；
3. 浮点误差可能造成少一分或多一分；
4. 微信回调的金额校验被关闭。

### 28.4 商品快照

1. `product_type` 没有按预期写入订单明细；
2. `product_points` 没有保存；
3. 微信回调重新读取当前商品名称、价格、类型和积分；
4. 商品修改可能改变历史订单权益；
5. 商品删除可能导致微信回调查不到完整订单商品。

### 28.5 订单字段

1. 订单没有保存 `seat_id`；
2. 订单没有保存本单 `points_earned`；
3. 金币支付没有保存 `paid_at`；
4. 金币成功响应读取错误的旧状态字段；
5. 订单号冲突时没有自动重试。

### 28.6 支付安全与幂等

1. 微信回调没有执行完整的请求签名验证；
2. 没有强制校验微信回调金额；
3. 没有校验商户号和应用 ID；
4. 没有明确校验微信交易状态；
5. 幂等检查没有使用订单行锁；
6. 并发回调可能重复发积分或酒券。

### 28.7 权益与账本

1. 金币和微信积分流水记录方式不一致；
2. 金币支付提交后才发权益；
3. 发权益失败无法回滚已完成的订单和扣款；
4. 酒券发放失败只记录日志；
5. 金币余额同时写入两套消费记录，职责重叠；
6. 缺少明确的权益发放幂等键。

### 28.8 打印

1. 打印机没有按门店筛选；
2. 所有启用设备都会收到订单；
3. 打印为同步远程请求；
4. 打印失败没有可靠重试任务；
5. 微信回调在数据库事务内调用打印系统；
6. 打印结果与订单状态没有独立记录。

---

## 29. 推荐的新系统功能规格

在其他系统中重新实现时，建议将功能拆成：

1. 创建订单；
2. 执行支付；
3. 统一处理支付成功；
4. 异步发放和打印。

### 29.1 第一阶段：创建订单

建议在一个本地事务中完成：

1. 验证当前用户；
2. 验证门店；
3. 验证桌位属于门店；
4. 验证座位属于桌位和门店；
5. 合并请求中的重复商品；
6. 锁定所有涉及的商品记录；
7. 验证商品状态和门店范围；
8. 验证合计购买量是否超过库存；
9. 使用整数分计算金额；
10. 保存完整商品快照；
11. 创建订单；
12. 创建订单明细；
13. 扣减或预占库存；
14. 提交事务。

### 29.2 建议保存的商品快照

每条订单明细至少保存：

- 商品 ID；
- 商品名称；
- 商品单价，单位为分；
- 商品类型；
- 商品赠送积分；
- 商品券规则；
- 购买数量；
- 商品小计，单位为分；
- 下单时使用的规则版本。

后续支付回调、积分和发券必须使用订单快照，不能重新使用商品当前配置。

### 29.3 微信支付

创建微信支付时：

1. 本地订单必须已经有唯一订单号；
2. 支付金额使用整数分；
3. 保存支付单；
4. 保存微信预支付标识；
5. 保存支付单过期时间；
6. 订单超时未支付后关闭支付单；
7. 释放预占库存。

微信回调必须：

1. 使用微信官方验证器验签；
2. 校验商户号；
3. 校验应用 ID；
4. 校验商户订单号；
5. 校验支付状态；
6. 校验币种；
7. 校验整数分金额；
8. 对订单或支付单加行锁；
9. 使用条件更新保证只完成一次；
10. 重复回调返回成功但不重复发权益。

### 29.4 金币支付

金币支付建议在同一个事务中：

1. 锁定订单；
2. 锁定用户余额账户；
3. 检查订单仍为待支付；
4. 检查余额充足；
5. 扣减余额；
6. 创建唯一账本流水；
7. 更新订单为已支付；
8. 保存支付时间；
9. 创建支付成功事件；
10. 提交事务。

### 29.5 统一支付成功处理

微信支付和金币支付应进入同一套“订单支付成功”业务。

统一流程：

1. 幂等地确认订单已支付；
2. 根据订单商品快照取得赠送积分；
3. 创建积分发放记录；
4. 增加用户积分；
5. 根据订单商品快照判断是否发券；
6. 按购买数量创建用户券；
7. 保存酒券明确过期时间；
8. 创建打印任务；
9. 发布订单已支付事件。

### 29.6 权益幂等

每种支付后权益都应设置唯一业务键。

建议格式：

```text
订单ID + 权益类型 + 订单明细ID + 序号
```

示例：

```text
10001:points:20001
10001:coupon:20002:1
10001:coupon:20002:2
10001:print:store-receipt
```

这样可以保证：

- 支付回调重试不重复增加积分；
- 不重复发放酒券；
- 单张酒券可以独立追踪；
- 打印任务可以安全重试。

### 29.7 事务后异步处理

积分、酒券和打印建议通过事务 Outbox 或可靠消息队列处理。

数据库事务内只保存：

- 订单状态；
- 支付结果；
- 账本流水；
- 待处理事件。

事务提交后由 Worker：

- 发放积分；
- 发放酒券；
- 创建过期任务；
- 按门店路由打印机；
- 重试失败任务；
- 记录每项任务状态。

### 29.8 打印任务

建议建立独立打印任务，至少保存：

- 订单 ID；
- 门店 ID；
- 打印类型；
- 打印内容快照；
- 目标打印机；
- 当前状态；
- 尝试次数；
- 最近错误；
- 下次重试时间；
- 打印成功时间。

打印机必须按照门店和业务类型进行路由，不能查询所有启用设备。

## 30. 推荐的最终订单状态流转

建议的支付状态：

```text
pending
  -> paid
  -> refunded

pending
  -> failed

pending
  -> closed
```

建议的餐品订单状态：

```text
pending_payment
  -> paid
  -> preparing
  -> ready
  -> completed
```

取消路径：

```text
pending_payment
  -> cancelled
```

退款路径：

```text
paid / preparing / ready
  -> refunding
  -> refunded
```

支付状态和餐品履约状态应分开管理，不能混为一个字段。

## 31. 推荐验收条件

新系统实现完成后，至少应通过以下验收场景。

### 31.1 正常场景

1. 单商品微信下单成功；
2. 多商品微信下单成功；
3. 单商品金币支付成功；
4. 多商品金币支付成功；
5. 普通商品正确发积分；
6. 酒券商品按数量发券；
7. 酒券30天后正确过期；
8. 订单小票只发送到对应门店打印机；
9. 微信支付成功后订单进入备餐状态；
10. 金币支付成功后订单进入备餐状态。

### 31.2 参数和商品异常

1. 商品数组为空；
2. 商品 ID 缺失；
3. 数量为零或负数；
4. 支付方式不合法；
5. 门店不存在；
6. 桌位不属于门店；
7. 座位不属于桌位；
8. 商品不存在；
9. 商品属于其他门店；
10. 商品已下架；
11. 商品库存不足；
12. 请求中重复提交同一商品。

### 31.3 支付异常

1. 金币余额不足；
2. 同一金币订单重复支付；
3. 微信支付金额不一致；
4. 微信回调签名无效；
5. 微信回调商户号不一致；
6. 微信回调应用 ID 不一致；
7. 微信回调重复到达；
8. 微信回调并发到达；
9. 微信支付超时未完成；
10. 微信预支付已创建但本地请求超时。

### 31.4 一致性和重试

1. 并发购买最后一份库存；
2. 积分 Worker 重试不重复加积分；
3. 酒券 Worker 重试不重复发券；
4. 打印失败后可以重试；
5. 打印重试不会影响订单和支付状态；
6. 支付成功后商品改价不影响订单金额；
7. 支付成功前商品改积分不影响订单权益；
8. 商品删除后仍能根据订单快照发放权益；
9. 接口超时后客户端重试不会重复创建订单；
10. 任何账本变更都能通过唯一流水追踪。

## 32. 总结

该方法的核心业务可以概括为：

```text
认证用户
-> 验证请求
-> 验证门店和商品
-> 计算金额与赠送积分
-> 创建订单和商品快照
-> 扣减库存
-> 微信或金币支付
-> 支付成功后发积分
-> 酒券商品按数量发券
-> 创建酒券过期任务
-> 写账本和日志
-> 打印门店小票
```

需要迁移的是这套业务能力，而不是当前方法的具体代码结构。

新系统应重点保证：

- 金额以整数分计算；
- 商品规则完整快照；
- 库存原子扣减；
- 支付回调完整验签和金额校验；
- 订单支付幂等；
- 积分、酒券和打印幂等；
- 金币和微信共用支付成功流程；
- 外部副作用异步执行；
- 打印机按照门店路由；
- 失败任务可追踪、可恢复、可重试。
