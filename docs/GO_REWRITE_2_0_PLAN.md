# InwardClub 现有功能、2.0 需求与 Go 重构实施总方案

> 本文是 2.0 的唯一工作基线，合并自当前 Laravel 项目代码、`routes/api.php`、`docs/inwardclub.sql`（现网结构导出）、`docs/InwardCLub2.0.xlsx`（2.0 功能清单）和 `docs/V1_API_INVENTORY_AND_V2_MAPPING.md`（v1 实际路由盘点与 v2 映射）。
>
> 数据仍在运营，任何 2.0 开发均以 `inwardclub.sql` 的真实表、历史主键和交易记录为准；不能仅依据 Laravel migrations 或旧接口文档推断数据结构。旧文档与代码存在漂移，例如门店后台文档写 `/store-admin`，实际路由前缀是 `/store`。
>
> 具体实现以 `docs/CLAUDE_GO_2_0_IMPLEMENTATION_SPEC.md` 为准；文件与图片接入以 `docs/QINIU_ASSET_SERVICE_SPEC.md` 为准。2.0 小程序不开放支付宝；门店后台的线下聚合收款码可接受微信和支付宝付款。
>
> `docs/V1_API_INVENTORY_AND_V2_MAPPING.md` 是接口覆盖检查表，不要求逐路径复制 v1，但要求所有已暴露业务能力在 v2 中明确标注为重建、合并、废弃或待确认。

## 1. 当前系统定位

InwardClub 当前是一个围绕线下门店的会员运营、预约、点餐、活动和收银系统。

主要用户端：

- 小程序端：用户登录、门店浏览、桌座预约、点餐、充值、活动购买、优惠券、积分/金币、排行榜。
- 门店后台：单店运营管理，包括用户、桌座、分类、餐品、活动、预约、订单、员工、收款、门店设置和统计。
- 总管理后台：系统级管理，包括门店、管理员、门店管理员、全局商品/活动/配置、会员、订单、Banner、充值产品、流水和统计。
- 员工/核销能力：小程序内的员工审核入口，用于积分审核、活动核销、今日活动和审核历史。

## 2. 当前技术栈与外部依赖

- 后端框架：Laravel 12 / PHP 8.2。
- 认证：JWT，区分小程序用户、管理员、门店管理员中间件。
- 微信能力：微信小程序登录、手机号解密、微信支付 JSAPI、支付通知、订单查询、退款。
- 图片上传：本地 public storage，多类型目录，带文件安全校验。
- 二维码：活动订单/核销码、桌码、员工二维码等。
- 云打印：芯烨云打印机，点餐、兑换券等场景会触发打印。
- 队列/定时：Laravel jobs/commands，用于优惠券过期、活动订单/餐品订单/充值订单状态更新等。

## 3. 功能域整理

### 3.1 认证与账户

小程序端：

- 微信小程序登录。
- JWT 刷新、退出、当前用户信息。
- 用户资料更新。
- 获取微信手机号。
- 头像上传。

后台端：

- 管理员登录、刷新、退出、当前管理员信息。
- 总管理员、门店管理员、收银员账号管理。
- 管理员角色主要包括 `super_admin`、`cashier`，并通过 `store_id` 做数据隔离。

Go 2.0 建议：

- 统一为 `auth` 模块，账号身份拆成 `member`、`admin`、`store_admin/staff/cashier` 三类 principal。
- JWT claims 必须带 `subject_type`、`role`、`store_id`、`token_version`，便于权限和强制下线。
- 工作人员 `staff` 身份只能绑定一个门店；同一微信用户/工作人员账号不得存在多门店 staff 绑定。小程序和门店后台均不提供 staff 选择门店能力。

### 3.2 门店、桌台、座位与预约

门店：

- 门店列表、详情、营业信息、Logo、地址、经纬度、营业时间、状态。
- 总后台可增删改查所有门店，并绑定/更新门店管理员。
- 门店后台只能管理当前门店信息。

桌台/座位：

- 桌台管理：桌号、桌名、座位数、状态、桌码。
- 座位管理：座位编号、类型、状态、备注。
- 小程序可查看门店桌台和座位状态。
- 小程序可预约座位。
- 系统提供自动清理/释放座位预约的接口。

预约：

- 用户创建、查看、取消预约。
- 门店后台创建、查看、更新、删除预约。
- 预约和桌台/座位状态存在联动。

Go 2.0 建议：

- 单独建 `store` 和 `reservation` 两个模块。
- 座位状态需要明确状态机：`available -> reserved -> occupied -> available`，维护/取消作为旁路状态。
- 预约释放必须由定时任务统一执行，不建议保留隐藏路径接口。

### 3.3 商品、分类与点餐

分类：

- 支持门店分类和全局分类。
- 支持父子分类、层级、排序、启用/禁用。
- 支持分类图片上传。

商品：

- 商品/餐品增删改查。
- 支持门店商品和全局商品。
- 字段包含分类、图片、描述、价格、库存、状态、积分、类型、排序。
- 支持批量上下架、批量排序、库存更新。

点餐订单：

- 小程序创建餐品订单，查询支付状态，查看订单列表和详情。
- 支持微信支付回调。
- 门店/总后台查看餐品订单，更新订单状态。
- 点餐订单可触发打印。

Go 2.0 建议：

- 建 `catalog` 模块管理分类和商品。
- 建 `food_order` 模块处理购物车快照、库存扣减、支付单生成、打印。
- 金额统一用整数分，避免浮点/decimal 跨语言误差。

### 3.4 活动与活动订单

活动：

- 门店活动和全局活动。
- 活动字段包含标题、图片、描述、内容、价格、开始/结束时间、状态。
- 总后台可创建全局活动，并分配到门店。
- 门店后台可管理本店活动。
- 小程序可浏览活动详情。

活动订单：

- 小程序购买活动。
- 支持微信支付通知。
- 活动订单有支付状态、使用状态、二维码/核销码、使用时间、有效期。
- 员工可审核/核销活动。
- 总后台可查看活动订单，并存在退款方法。

Go 2.0 建议：

- 建 `activity` 模块。
- 活动购买应复用统一支付单能力，不要让活动、充值、点餐各自散落支付逻辑。
- 核销建议引入一次性 verification code，避免只靠二维码 URL。

### 3.5 会员、积分、金币、余额与流水

会员：

- 会员列表、详情、更新、删除。
- 会员充值。
- 会员等级列表与后台管理。
- 排行榜。

积分：

- 积分记录、积分统计。
- 用户存积分。
- 用户积分提现/审核。
- 邀请奖励积分。
- 签到模型存在，但当前路由未明显暴露完整签到接口。

金币/余额/充值：

- 快捷充值产品 `coin_product`。
- 小程序创建充值订单、查询状态、支付回调。
- 用户交易流水。
- 余额/积分消费记录服务。

优惠券：

- 用户优惠券列表。
- 用户兑换优惠券。
- 兑换可能触发打印。
- 存在优惠券订单明细模型。

Go 2.0 建议：

- 建 `wallet` 模块，统一管理积分、金币、余额、充值和流水。
- 所有资金/积分变动必须走 ledger：一条业务单据 + 多条账本记录。
- 明确积分、金币、余额三者边界，避免字段语义混乱。

### 3.6 支付、退款与订单状态

当前支付入口：

- 通用支付：创建订单、查询、退款、支付通知。
- 活动支付：活动购买和活动通知。
- 充值支付：充值下单、查询、通知。
- 点餐支付：点餐下单、查询、通知。

当前问题：

- 支付逻辑分散在多个 Controller。
- 各类订单状态字段不完全统一。
- 金额字段存在 decimal/分单位混用风险。
- 支付回调幂等需要重点核验。

Go 2.0 建议：

- 建 `payment` 模块，提供统一支付单 `payment_orders`。
- 业务订单只关心业务状态，支付状态由支付单驱动。
- 支付回调必须用 `out_trade_no` 幂等锁，重复通知只返回成功，不重复加金币/发券/核销。
- 小程序支付方式固定为微信和金币；门店后台新增聚合收款单和动态收款码，由受控收单渠道接受微信/支付宝线下扫码。创建收款码时可选填已注册会员手机号，付款成功后按已锁定的会员归属异步执行返金币、积分等规则；未绑定会员的散客收款不发放会员权益。支付宝绝不出现在小程序接口或 UI 中。

### 3.7 图片上传与文件安全

当前能力：

- 管理后台和门店后台均有图片上传接口。
- 支持单图、多图、删除、文件信息、上传配置。
- 上传类型包含头像、会员等级、商品/分类等目录。
- `FileSecurityService` 做扩展名、MIME、文件头尾、恶意内容扫描、图片完整性校验和安全文件名生成。

Go 2.0 建议：

- 建 `asset` 模块。
- 上传元数据入库，业务表只存 `asset_id` 或规范化 URL。
- 保留文件安全校验，Go 版可用 magic bytes + image decode + 大小限制 + 路径白名单。

### 3.8 打印与硬件集成

当前能力：

- 芯烨云打印机接口封装。
- 添加/删除/更新打印机。
- 打印文本、标签、小票格式化。
- 查询订单状态、打印机状态、队列、统计、蜂鸣器。
- 点餐订单、券兑换、积分提现等场景可能触发打印。

Go 2.0 建议：

- 建 `printer` 模块和异步打印任务。
- 业务请求只落库打印任务，不同步等待云打印，减少支付回调和下单接口超时风险。

### 3.9 统计、日志与后台运营

统计：

- 总后台 dashboard：营收、用户、预约、门店表现、总览等。
- 门店后台 dashboard：销售、趋势、热门商品、用户活跃。
- 全记录统计 `all-record/stats`。

日志：

- 操作日志、登录日志、错误日志、日志统计、清理逻辑在控制器里存在，但当前路由只暴露部分。

Go 2.0 建议：

- 建 `reporting` 模块，区分实时统计和离线汇总。
- 审计日志作为横切能力进入中间件，不要在业务代码里零散写。

## 6. Go 2.0 推荐模块划分

推荐从一个模块化单体开始，不建议一上来拆微服务。

```text
cmd/api
internal/bootstrap
internal/http
internal/auth
internal/member
internal/store
internal/catalog
internal/reservation
internal/order
internal/activity
internal/wallet
internal/payment
internal/coupon
internal/asset
internal/printer
internal/reporting
internal/admin
internal/auditlog
internal/job
pkg/ecode
pkg/pagination
pkg/timeutil
pkg/wechat
pkg/xpyun
```

建议技术选择：

- HTTP：Chi，保持路由、中间件和测试实现一致。
- DB：PostgreSQL 或 MySQL 均可；若沿用现库，优先 MySQL。
- SQL：推荐 `sqlc` 或 `gorm`。资金账本建议用显式 SQL，减少 ORM 魔法。
- 迁移：goose / atlas。
- 配置：env + yaml，敏感信息全部走环境变量/密钥管理。
- 队列：Redis + Asynq，或先用数据库任务表。
- 日志：zap/slog，结构化 JSON。
- OpenAPI：以 Go handler 注解或独立 OpenAPI yaml 维护契约。

## 8. 需要重点清理的问题

- 文档与路由不一致，需要以实际调用为准重建 API 契约。
- 支付逻辑分散，2.0 必须统一支付单和回调幂等。
- 金额单位混杂，2.0 统一使用整数分。
- 模型字段与迁移文件不一致，需要完整 DDL baseline。
- 部分测试接口和隐藏系统接口不应进入 2.0。
- 配置中存在默认微信小程序敏感配置示例，2.0 应全部改为必填环境变量。
- 图片 URL 生成散落在模型访问器中，2.0 应统一由 asset 服务处理。
- 打印同步调用有超时风险，2.0 应改为异步任务。

## 10. 下一步建议

### 11.2 总后台与门店后台

总后台和门店后台的活动、餐品、积分商城、券、订单、用户、Banner、桌座、打印机、交易日志等功能高度重叠。2.0 不建立两套业务服务，而是建立同一套资源和策略；但前端站点、账号体系、登录入口、token audience 和 API 权限边界必须独立。总后台拥有全局范围，门店后台的查询和写入强制注入 `store_id` 范围。

| 领域 | 总后台权限 | 门店后台权限 | 2.0 统一对象 |
| --- | --- | --- | --- |
| 门店与规则 | 全部门店、全局默认规则 | 仅本店资料与可覆盖配置 | `stores`、`store_settings`、规则发布版本 |
| 商品/积分商城/券 | 全局模板、跨店投放、审核 | 本店商品、价格/库存覆盖、兑换范围 | `catalog_items`、`catalog_variants`、`coupon_templates` |
| 活动 | 创建全局活动、分配门店 | 创建和运营本店活动 | `activities`、`activity_sessions`、`activity_ticket_types` |
| 订单/退款/统计 | 全局检索、退款审核、全局统计 | 仅本店订单、收款、退款权限范围 | 统一订单视图、支付单、报表快照 |
| 用户/会员资产 | 全局用户、规则、人工调账审批 | 本店用户视图、受控发放/审核 | `members`、资产账本、福利发放记录 |
| 运营资源 | 全局 Banner、默认背景、OSS 配置 | 本店 Banner、桌座背景、打印机 | `assets`、`banners`、`printer_devices` |
| 线下聚合收款 | 收单渠道配置、跨店报表/退款审批 | 输入可选会员手机号创建本店动态码、查看和操作本店收款单 | `offline_collection_orders`、`payment_orders`、资产账本 |

后台商品、券、活动的具体接口清单、DTO、筛选条件、门店独立覆盖规则和权限矩阵，以 `docs/CLAUDE_GO_2_0_IMPLEMENTATION_SPEC.md` 第 8.7 节为准。商品、券、活动必须支持“总后台全局模板/投放”和“门店后台本店自有/本店覆盖”两类需求。

### 11.3 2.0 规则不得写死

以下内容在表格中有具体数值，但运营会调整，必须作为带生效时间的后台规则保存，不能进入 Go 常量或小程序代码：连续签到梯度、签到/到店低消门槛、20:30 前额外奖励、邀请奖励和返佣比例、充值档位奖励、积分/金币/余额兑换比例、VIP 升级门槛、每日/月度福利、券面值和有效期、活动支付方式和票档库存。

建议规则对象至少具备 `store_id`（允许全局默认）、`rule_type`、`version`、`effective_from`、`effective_to`、`status`、`definition_json`、`published_by`。支付/发放时把命中的规则版本写入订单或账本，保证历史可追溯。

## 12. 现有数据库基线与保留策略

### 12.1 已确认的现网表

`docs/inwardclub.sql` 共包含 37 张表，其中 29 张为可迁移业务表；`cache`、`cache_locks`、`jobs`、`failed_jobs`、`job_batches`、`sessions`、`migrations`、`password_reset_tokens` 为 Laravel 运行表，不迁移业务数据，只在 Go 环境按新基础设施重建。

| 领域 | 现网表 | 处理方式 |
| --- | --- | --- |
| 会员与身份 | `users`、`admins`、`staff`、`vip_level`、`invitations`、`sign_in` | 保留主键和创建时间；拆分身份、会员等级、签到、邀请规则时保留 `legacy_*_id` |
| 门店与预约 | `stores`、`tables`、`seats`、`reservations` | 原样迁入首版；补充背景资产、预约时间窗、到店/排队字段 |
| 商品与内容 | `categories`、`products`、`banner`、`settings` | 原样迁入，并逐步把图片 URL 归档到资产表；全局和门店范围保持不变 |
| 活动 | `activities`、`activity_orders` | 历史活动和订单原样保留；新增规格/票券表只服务 2.0 新活动，不反向改写旧单 |
| 点餐 | `food_orders`、`food_order_items` | 订单号、金额、支付/业务状态和商品快照不可变；补建统一支付关联 |
| 充值与资产 | `recharge`、`coin_product`、`user_points`、`save_points`、`points_withdrawal`、`points_consumption_records`、`balance_consumption_records`、`transaction_records` | 迁入历史流水并生成期初余额校验；新交易只写新账本 |
| 券与兑换 | `user_coupon`、`coupon_order_items` | 保留用户券状态、过期时间和兑换历史；补券模板/适用范围/兑换订单 |
| 设备 | `printer_device` | 原样保留设备序列号和门店归属；凭据进入密钥配置，不落日志 |

### 12.2 当前 DDL 暴露的关键差异

1. 现网导出使用 `points_withdrawal`、`user_coupon` 单数表名，而旧整理/模型文档中出现 `points_withdrawals`、`user_coupons`；Go 迁移脚本必须以 SQL 导出为准。
2. `users` 同时存在 `total_points`、`used_points`、`points`、`balance`、`all_balance` 等资产字段，语义不能直接假定。必须用各流水表重算，并与当前展示余额逐用户对账。
3. `food_orders`、`activity_orders`、`recharge` 各自保存支付状态、渠道、交易号；2.0 用统一支付单关联它们，但历史行不应被强制改成同一种状态枚举。
4. 现网金额大量为 `DECIMAL`，2.0 内部新列统一 `*_cent BIGINT`；历史金额通过精确乘 100 转换并保留原金额或源表引用，禁止浮点转换。
5. 外键并不覆盖所有业务关联，且全局/门店商品通过 `store_id IS NULL` 表示。迁移前需要做孤儿记录、重复订单号、无效状态和图片 URL 的数据质量报告。

### 12.3 目标数据模型

保留 MySQL 作为 2.0 首选数据库，降低迁移风险。新表使用 `bigint unsigned` 主键、UTC 时间、整数分金额；历史表可先作为只读兼容表，逐步下线。

```text
members / staff_accounts / admin_accounts
stores / store_settings / tables / seats / reservations / waitlist_entries
catalog_categories / catalog_items / catalog_variants / store_item_overrides
activities / activity_sessions / activity_ticket_types / activity_orders / tickets / verifications
business_orders / food_orders / order_items / recharge_orders / redemption_orders
payment_orders / payment_transactions / refund_orders
wallet_accounts / wallet_ledger_entries / wallet_holds
coupon_templates / coupon_entitlements / coupon_redemptions
membership_tiers / membership_benefit_rules / benefit_grants
rule_definitions / rule_executions
assets / banners / printer_devices / print_jobs
audit_logs / outbox_events / idempotency_keys / reporting_daily
legacy_id_maps / migration_runs / reconciliation_results
```

`wallet_accounts` 只保存可快速读取的当前余额；真实来源是不可变的 `wallet_ledger_entries`。账户至少区分 `points`、`coins`、`cash_balance`、`growth_value`，不允许用一个字段兼任不同资产。

## 13. 数据迁移与不停业切换方案

### 13.1 基本原则

- 不直接在生产库“改表重构”；新建 2.0 数据库和 Go 服务，旧系统持续提供写入。
- 历史业务单、支付交易号、用户/门店/商品主键和创建时间保留可追溯映射。
- 迁移可以重跑，所有导入作业必须幂等，并记录批次、源主键、校验结果和失败原因。
- 先迁静态数据和历史数据，再增量同步，最后按功能灰度切流；任一阶段可回退到 v1。

### 13.2 执行阶段

| 阶段 | 产物与动作 | 放行条件 |
| --- | --- | --- |
| A. 盘点 | 生产库只读 DDL/数据快照、表行数、字段空值、枚举值、外键/孤儿记录报告 | 业务确认所有资产字段和订单状态含义 |
| B. 目标库 | 版本化 MySQL migration、字典数据、`legacy_id_maps`、迁移审计表 | 测试环境可从空库重复建库 |
| C. 全量回灌 | 按“门店/会员 -> 商品 -> 订单 -> 流水/券”导入；历史表保留源记录引用 | 行数、主键映射、金额合计、资产余额四类校验通过 |
| D. 增量同步 | 旧库变更通过 binlog/CDC 或经过审核的双写 outbox 同步至 2.0 | 连续 7 天延迟和对账无未解释差异 |
| E. 影子验证 | Go 服务只读请求影子比对 v1；支付回调仍只由 v1 处理 | 核心读接口正确率、性能与权限校验达标 |
| F. 灰度写入 | 先切 Banner/商品等低风险后台，再切新订单；支付回调每类业务只允许一个系统消费 | 每个切换点均有开关、监控、回滚脚本和负责人 |
| G. 收尾 | 旧库冻结为只读历史库；完成最终增量、全量对账和备份演练 | 财务、运营和技术共同签字确认 |

### 13.3 必做对账

迁移工具每次执行必须输出以下可审计结果：每表记录数与主键覆盖率；每门店/日期的已支付餐品、活动、充值金额；每用户的积分、金币、余额期初/期末；未使用活动票和未过期用户券数量；支付交易号唯一性；无法关联的用户、商品、门店或订单清单。任何资产余额差异不得通过“直接改余额”消除，必须以带原因、审批人和源记录的调整账本修正。

### 13.4 历史资产导入规则

1. 为每个用户建立四类 2.0 钱包账户，并写一条 `migration_opening_balance` 账本行。
2. 期初数以经过确认的现网展示余额为候选值，同时用 `user_points`、消费/存取积分记录、`transaction_records`、`balance_consumption_records` 回放校验。
3. 无法完全回放的旧记录不丢弃：保留源表、源主键、原始 JSON/字段快照，并建立人工差异队列。
4. 历史订单迁入为 `legacy` 来源；其退款、核销和展示仍可读取。新规则不追溯发放历史权益，除非运营明确批准补发。

## 14. 关键业务规则与待确认事项

以下事项影响金流、资产和会员权益，不能由技术自行猜测；在实现对应模块前应由业务以规则表确认。

| 事项 | 当前描述中的冲突或缺口 | 建议决议 |
| --- | --- | --- |
| 金币与余额 | 表格称“充值的是余额可用于点餐”，现网同时有 `balance`、`all_balance`、金币相关流水 | 明确金币是否可消费、余额是否可提现、两者是否可互转；2.0 必须分账户 |
| 积分存取/下分 | 规则涉及水上/水下、带入、时间、比例和历史提取记录 | 将输入、公式、审批、证据、规则版本写入 `save_points` 新流程；先做业务验算样例 |
| 低消判定 | 88 元、酒券、20:30、到店、VIP 的组合条件多处出现 | 指定“可计入订单类型/支付方式/退款后处理/自然日时区/一次还是多次”的正式定义 |
| 邀请奖励 | 有积分 2000、现金流 10% 金币奖励、首次充值/低消条件 | 明确奖励对象、上限、退款冲正、是否跨门店；奖励仅在支付最终成功后入账 |
| 活动多票一码 | 一次购买多张但一个核销码 | 定义一码可核销 N 次还是一次核销全部；推荐生成 N 张票、订单提供聚合码 |
| 券模型 | 券值、兑换商品、餐品复用在表格中仍待定 | 推荐券模板定义适用分类/商品和面值，兑换时引用商品快照；禁止复制第二套餐品库 |
| VIP 规则 | 表格列出 VIP1-8，但现网 `vip_level` 字段仅 `level/name/points/image/status` | 把升级条件、日福利、月福利拆为版本化规则，按发放记录幂等执行 |

## 15. Go 2.0 实施清单

### 15.1 技术与工程基座

1. 建立 Go 模块化单体：Chi 或 Gin、MySQL、Redis、Asynq/数据库任务、OpenAPI、结构化日志和指标。
2. 建立版本化 schema migration、种子数据、脱敏生产快照导入和迁移/对账 CLI。
3. 完成认证、RBAC、门店数据范围中间件、请求幂等键、审计日志、outbox 事件和统一错误码。
4. 对外从 `/api/v2/mini`、`/api/v2/store`、`/api/v2/admin` 发布；v1 只作兼容层，禁止继续增加隐藏测试入口。

### 15.2 推荐交付顺序

| 里程碑 | 可上线范围 | 前置条件 |
| --- | --- | --- |
| M0：数据基线 | DDL、迁移工具、对账报告、只读数据访问 | 完成第 13 节 A-C |
| M1：低风险读服务 | 门店、Banner、分类、商品、活动浏览、VIP、充值档位 | API 契约冻结、影子比对通过 |
| M2：会员与资产 | 登录、资料、钱包/账本、签到、邀请、券展示 | 钱包语义和规则确认 |
| M3：交易闭环 | 点餐、充值、活动支付、退款、微信支付回调、金币扣减、门店聚合收款码（微信/支付宝）、打印任务 | 每个支付渠道的回调消费者唯一且幂等 |
| M4：预约与履约 | 桌座预约、排队、到店、低消奖励、核销、员工审核 | 到店/低消规则确认 |
| M5：运营后台 | 总后台/门店后台统一资源权限、报表、审计、规则发布 | 关键业务灰度稳定 |
| M6：增强能力 | 活动规格、积分商城、会员福利、排行榜、OSS/CDN | 规则引擎与历史数据对账稳定 |

### 15.3 验收红线

- 支付通知、退款、券核销、福利发放、资产变动必须幂等；重复请求不能重复扣款、加分或发券。
- 所有金额使用整数分；所有资产变化必须有可逆/可解释的账本记录。
- 门店后台不能通过参数越权访问其他门店任何数据。
- 新旧切换期间同一种业务订单只能由一个系统写入和消费支付回调。
- 每次发布前运行数据迁移回归、账本对账、权限隔离和支付回调重复投递测试。
