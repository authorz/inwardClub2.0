# InwardClub 2.0 全局设计规则

本文件用于约束 Codex 后续自主延伸页面时的视觉、交互和业务边界。Codex 开发前必须阅读本文件，并在交付说明中声明是否遵守。

## 1. 总原则

- 产品 UI chrome 以黑、白、浅灰为主：文字、按钮、分割线、表单、导航、弹层、列表均遵守该规则。
- 内容图片允许有节制的真实色彩：Banner、活动海报、商品图、头像、门店图不强制灰度化。
- 页面要大气、简洁、克制，优先清晰的信息层级和可操作性。
- 列表优先使用通栏布局、分割线、轻背景区块；避免重阴影卡片堆叠。
- 不使用紫蓝渐变、彩色餐饮促销风、红色优惠券市场风、金色奢华钱包风。
- 不使用无意义装饰：渐变球、光斑、浮动贴纸、复杂插画、玻璃拟态。
- 不做卡片套卡片，不做过深层级的框中框。
- 字号必须可读，按钮文字不得溢出，移动端触控目标必须足够大。
- AI 设计图中的错字、示例门店、示例金额、示例时间、示例订单号不得照抄，业务字段以接口文档为准。

## 2. 小程序规则

- 底部菜单固定为：`首页 / 预约 / 点餐 / 我的`。
- 底部菜单图标必须使用 `design/mini-program/tab-icons/` 中定稿 SVG，不得使用 AI 图临时生成图标。
- 不实现签到页面、签到入口、签到弹窗。
- 小程序不出现支付宝；支付方式只允许微信和金币。
- 微信右上角胶囊、状态栏、安全区使用小程序原生能力，不照抄 AI 图中的临时系统 UI。
- 首页以 `design/mini-program/final/home/01-home-final-iphone17.png` 为准。
- 活动列表以相册式堆叠轮播为业务例外；其他页面不得滥用堆叠卡片和重阴影。
- 点餐页必须左侧分类栏、右侧两列商品，每个商品有数量步进器。
- 预约页必须支持多桌；每张德州扑克桌固定 9 个座位。
- 个人中心及子页面以 `design/mini-program/final/member-center/`、`design/mini-program/final/member-subpages/`、`design/mini-program/final/member-asset-sheets/` 为准。
- 个人中心点击金币弹出充值金币底部弹层；点击积分弹出存取积分底部弹层；钱包流水作为二级入口。
- 金币充值只允许微信支付，不出现金币支付金币、提现、银行卡、现金到账。
- 存取积分固定当前门店，不能切换门店、门店下拉或跨店选择，提交后由工作人员审核。
- 二维码、核销码、兑换码必须由接口返回或前端根据接口数据生成；设计图中的码只作视觉占位。

## 3. 小程序字体层级与字号硬规范

- 默认字体：遵守 `mini-program/miniprogram/styles/vars.wxss`；iOS/macOS 优先 `-apple-system` / `PingFang SC`，其他中文环境按 `Noto Sans CJK SC` / `Source Han Sans SC` / `Microsoft YaHei UI` / `Microsoft YaHei` 顺序回退。
- 字号档位表（新增或修改页面必须落在以下档位内）：

| 用途 | 字号 | 字重 | 备注 |
| --- | --- | --- | --- |
| 页面一级标题 | 30rpx | 600/700 | 常规文字字号上限 |
| 区块标题 | 28rpx | 600 | 必要时 700，但不能滥用 |
| 重要正文/表单项/列表主信息 | 26rpx | 400/500 | |
| 正文 | 24rpx | 400 | |
| 次要说明 | 22rpx | 400 | |
| 弱提示/tag/状态辅助 | 20rpx | 400 | |
| 极小辅助信息 | 18rpx | 400/600 | 仅限排行榜装饰标签等高密度短文本，不得用于正文 |
| 图形内微字 | 16rpx | 400/600 | 仅限紧凑徽标、图片占位品牌字，不得用于说明文本 |
| 重要数字 | 30rpx | 600/700 | 必须使用 `tabular-nums` 或同等数字稳定策略 |

- 表单 item 高度默认 44px，也就是 88rpx；特殊弹层表单不得低于 44px 视觉高度。
- 新增或修改页面不得随意新增字号；必须新增时，交付说明必须写明原因、适用范围、为什么不能归入现有档位。
- 字符图标和纯装饰符号不属于文字字号档位，但必须通过独立语义类控制，不能借此放大正文或数字。
- 页面局部 wxss 中允许写 `font-size`，但必须落在上述档位；优先复用 `tokens.wxss` 中的 `ic-title` / `ic-h2` / `ic-body` / `ic-sub` / `ic-num` / `ic-cell` / `ic-btn` 等公共类。
- 设计稿还原时，视觉接近优先，但最终代码必须回到字号规范档位，不能照抄 AI 图里的随机字号。

## 4. 总后台规则

- 总后台是独立站点、独立账号、独立登录入口、独立 token audience。
- 总后台可以管理全局模板和跨店数据：门店、员工、全局商品、活动模板、券模板、Banner、充值产品、VIP/权益规则、报表、审计等。
- 总后台 UI 应偏运营工作台：密度适中、表格清晰、筛选明确、批量操作谨慎。
- 总后台不得复用门店后台账号体系或路由守卫。
- 涉及资金、资产、规则、退款、钱包调整的操作必须有权限码、审计记录和二次确认。
- 不做营销落地页式后台，不做大 Hero，不做装饰型数据大屏。

## 5. 门店后台规则

- 门店后台是独立站点、独立账号、独立登录入口、独立 token audience。
- 门店后台只能操作当前门店 scope，不能跨店查询或跨店操作。
- 工作人员只能绑定一个门店，不能选择门店，不能切换门店。
- 门店后台可以管理本店商品、库存/价格覆盖、本店活动、订单处理、核销、积分审核、线下聚合收款、打印机等。
- 门店后台不得创建全局模板，不得访问总后台权限码。
- UI 应偏一线操作台：清楚、直接、少装饰、任务状态明显。

## 6. 服务端与接口规则

- 服务端以 `docs/CLAUDE_GO_2_0_IMPLEMENTATION_SPEC.md` 为主规格。
- 小程序、总后台、门店后台的认证中间件、权限码、数据 scope 和审计上下文必须分开。
- 不能把积分、金币、余额、VIP、低消、邀请、充值档位等运营数值写死在 Go 或前端。
- 规则必须来自后台配置或规则表，并保留生效时间、幂等键和审计。
- 小程序 API 不出现支付宝字段；支付宝只允许存在于门店线下聚合收款渠道和回调记录中。
- 所有写接口必须考虑幂等、权限、状态机和审计。
- 订单、支付、钱包账本、券、核销、积分审核必须按状态机实现，不能用前端状态代替服务端状态。

## 7. Codex 自主延伸页面要求

当 Codex 需要补充未出设计图的页面时：

- 必须先从已定稿页面抽取组件语言，不得重新发明视觉体系。
- 必须采用严格开发模式：先识别可复用模式，再抽公共组件、公共 hooks/composables、公共 API client、公共状态模型。
- 重复出现两次及以上的 UI、表单、表格、弹层、列表行、状态标签、上传、确认弹窗、分页、筛选、请求处理，必须抽为公共组件或公共工具。
- 禁止复制粘贴同类页面实现后只改字段；同类页面必须通过配置、props、schema 或组合式函数复用。
- 小程序新增页优先复用白底、细分割线、黑色主按钮、轻灰辅助区块。
- 后台新增页优先复用表格、筛选、抽屉、弹窗、二次确认和审计说明。
- 新页面若涉及金流、资产、跨店权限、核销、退款、钱包调整，必须先在任务回复中列出风险点和接口依据。
- 不确定业务规则时，必须留 `TODO: 待业务规则配置`，不得自行写死。
- 交付时必须列出参考的设计图路径、接口路径、权限码、验收方式和未决问题。

## 8. 公共组件与工程化规则

所有端必须遵守：

- API 调用必须走统一 request client，不允许页面内直接散落 `fetch`、`wx.request`、`axios` 实例。
- 登录态、权限、错误处理、loading、分页、空状态、确认弹窗必须有统一实现。
- 表单校验规则必须集中定义或可复用，不允许每页手写一套相同逻辑。
- 状态枚举、支付方式、订单类型、资产类型、核销状态必须集中定义，不允许散落字符串。
- 样式 token、颜色、间距、字号、圆角、分割线必须集中定义。
- 后台两端使用同一套开发模式，但不能共享运行时登录态、权限上下文或 API client 实例。
- 小程序端重复区块必须组件化：tabbar、bottom sheet、segmented control、stepper、asset strip、order row、ticket row、coupon row、empty state、loading state。
- 服务端重复能力必须平台化：config、logger、errors、authn、rbac、idempotency、audit、pagination、transaction、outbox、DTO envelope。
